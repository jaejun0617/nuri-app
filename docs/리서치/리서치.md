## 2026-06-30 Animal Hospital coordinate audit와 V1.1 추가 업데이트 planning

### 배경

신규 QA 계정 E2E와 navigation/back audit 이후 우리동네 병원 찾기의 public active 5,427건은 전국 기반을 갖춘 상태로 확인됐다. 남은 질문은 coordinate missing 122건이 release blocker인지, 아니면 데이터 품질 보강 후보인지였다. 동시에 PO가 V1.1 추가 업데이트 후보 8개를 제안했으므로 구현 착수 전에 공식 작업서와 진행률 기준을 먼저 만들어야 했다.

### 문제

좌표가 없는 병원을 가까운순 리스트에 그대로 섞으면 현재 위치 UX가 깨질 수 있다. 반대로 주소와 전화번호가 있는 public active 병원을 모두 숨기면 검색 정보 가치가 줄어든다. V1.1 추가 기능도 정책 미확정 상태에서 구현부터 시작하면 streak, XP, 알림, 무지개다리 상태 전환처럼 민감한 기능이 운영 리스크로 번질 수 있다.

### 결정

Animal Hospital coordinate missing 122건은 release blocker가 아니다. public active 5,427건 중 122건은 좌표가 없지만 모두 primary address를 가지고 있고, 82건은 official phone을 가진다. nearby 좌표 기반 리스트는 좌표가 있는 병원만 반환하고, text search/detail에서는 주소와 전화번호가 있으면 정보형으로 안전 표시한다. 좌표 기반 지도/길찾기 URL은 없으면 열지 않는다.

V1.1 추가 업데이트 8개는 `docs/planning/v1.1-additional-update-plan-and-checklist.md`를 공식 source of truth로 둔다. 1차 MVP는 회원탈퇴 입력 확인, 최근 로그인 표시, 타임라인 카테고리 count다. 데일리 streak와 XP/칭호는 PO 정책표 확정 전까지 구현하지 않는다.

### 리스크

- coordinate missing 122건은 데이터 품질 보강 후보로 남는다. 이번 기준 DB write나 seed 수정은 하지 않는다.
- 알림, XP, streak는 abuse 방어와 서버 계약 없이 UI만 먼저 만들면 운영 리스크가 커진다.
- 무지개다리 상태 전환 후 서비스 제안은 문구와 노출 빈도 정책이 확정되기 전까지 구현하지 않는다.

## 2026-06-21 NURI 전국 seed 3차/4차 확대와 권역별 gate 적용

### 배경

전국 seed 2차와 Kakao Local hard delete closeout 판정 이후 approved/public/active POI는 685건이었다. Kakao Local hard delete는 shared provider 의존성 때문에 보류됐지만, 자체 POI 전환을 진행하려면 검증 가능한 전국 주요 산책 권역 coverage를 계속 늘려야 했다.

### 문제

전국 확대를 무검증 대량 import로 처리하면 source/attribution, 좌표 품질, rollback, public projection safety가 약해진다. 반대로 seed 확대를 미루면 gate 적용 가능 권역이 늘지 않아 Kakao fallback 축소 효과가 제한된다.

### 선택지

- 전국 seed 3차만 처리하고 4차는 다음 턴으로 분리한다.
- source/attribution과 rollback이 명확한 3차/4차 후보를 같은 턴에서 batch를 분리해 처리한다.
- Kakao Local hard delete를 먼저 재시도하고 seed 확대는 보류한다.

### 결정

두 번째 선택지를 채택했다. 전국 seed 3차 batch `badb210c-3cb3-4643-a812-032222d415b4`로 180건, 전국 seed 4차 batch `b8fc90fa-7680-48ba-9cdf-d7638b4a2c7e`로 120건을 admin import/review workflow로 승인했다. 총 approved/public/active POI는 985건이 됐다. 신규 15개 권역은 모두 3km/5km coverage와 public nearby/search/detail smoke를 통과해 권역별 fallback gate를 추가 적용한다.

### 리스크

- 전국 전체 broad gate는 아직 적용하지 않는다. 도시 전체 단위로 묶으면 미처리 구역 UX가 나빠질 수 있다.
- Kakao Local hard delete는 여전히 보류다. Ready 권역 차단은 유지하지만 gate 밖, RPC error, 좌표 없음, detail missing, feature flag off 조건은 Keep Fallback으로 유지한다.
- 신규 seed는 operator-reviewed seed로 관리하며, 공공/OSM bulk import가 아니므로 전국 전체 coverage 완료로 표현하지 않는다.

## 2026-06-20 NURI Kakao Local hard delete closeout 판정

### 배경

Ready 권역에서 POI RPC 정상 응답 시 Kakao Local 호출을 0으로 막는 1단계 closeout은 완료됐다. 다음 판단은 산책/location discovery의 Kakao Local runtime을 실제로 hard delete할 수 있는지, 그리고 Android 실기기 detail tap 증적이 충분한지였다.

### 문제

Kakao Local provider는 산책 Ready fallback만의 코드가 아니다. 산책 Keep Fallback 조건, 반려동물 동반 장소 검색, 동물병원 provider matching, 좌표-행정동 변환 Edge Function이 같은 provider 또는 Edge Function 경로를 공유한다. 이 상태에서 hard delete를 진행하면 gate 밖 좌표, RPC error, 좌표 없음, detail missing, feature flag off 조건의 UX가 깨질 수 있다.

### 선택지

- Kakao Local runtime을 전부 hard delete한다.
- Ready 권역 차단은 유지하고 shared provider와 Keep Fallback 계약이 분리될 때까지 hard delete를 보류한다.
- Kakao Local closeout 판단 없이 seed 확대만 계속한다.

### 결정

두 번째 선택지를 채택한다. 이번 턴의 판정은 `hard delete 보류`다. Ready 권역 Kakao 호출 차단은 유지하고, Kakao Login/OAuth는 수정하지 않는다. Android `SM_S937N`에서 Galaxy 멀티윈도우를 유지한 채 고양/일산, 광주, 하남·미사 카드 tap → 상세 진입을 확인했다. approved/public/active POI는 685건으로 유지하고 전국 seed 3차는 closeout 우선순위 때문에 문서화만 유지한다.

### 리스크

- shared provider 분리 없이 hard delete하면 반려동물 동반 장소 검색, 동물병원 provider matching, coord2region 경로가 깨질 수 있다.
- 한글 검색어 실기기 입력은 Samsung keyboard shell input 제약이 있어 검색 결과 카드 tap 증적은 deep link/리스트 카드 tap과 public search RPC로 보완했다.
- Kakao Local hard delete는 separate closeout에서 provider 분리, safe fallback UX, feature flag off 계약을 먼저 고정해야 한다.

### 다음 액션

1. Kakao Local provider 분리 또는 safe fallback 대체 설계
2. 전국 seed 3차 확대

## 추가 메모: 2026-06-16 V1.1 walk POI 수도권 2차 coverage / gate 적용 권역 empty UX 검증

### 배경

북서울꿈의숲과 성남·분당·판교·탄천까지 gate가 확장되면서, gate 내부 empty case가 Kakao fallback으로 다시 빠지지 않는지 확인해야 했다. 동시에 수도권 coverage는 성남·분당·판교·탄천 1개 권역에 제한돼 있어, 다음 권역을 작은 batch로 확장할 필요가 있었다.

### 문제

gate 적용 권역이 늘어날수록 coverage가 충분하지 않은 지역에서 fallback을 닫는 리스크가 커진다. 반대로 coverage가 충분한 권역에서 계속 Kakao fallback을 허용하면 자체 POI 전환의 비용 방어 효과가 약하다. 신규 seed는 public/admin 표시값 한글 기준을 유지해야 하며, source/attribution과 rollback 기준이 불명확한 후보는 승인하면 안 된다.

### 선택지

- 수도권 2차를 문서화만 유지: 안전하지만 coverage 확장이 지연된다.
- 하남·미사, 수원·광교, 과천·서울대공원 3개 권역만 seed 착수: Android smoke와 rollback 범위가 현실적이다.
- 수도권 전체 gate 일괄 적용: coverage 부족 UX 리스크가 커서 배제한다.
- analytics SDK를 새로 도입해 fallback 비율을 계측: 이번 턴 범위를 넘고 운영 비용/의존성이 늘어 배제한다.

### 결정

수도권 2차는 하남·미사한강공원, 수원·광교호수공원, 과천·서울대공원 3개 권역으로 제한해 `operator-seed` admin import/review workflow로 60건 승인했다. import batch는 `d03e7cef-fb93-4b45-9e61-ec0c926952da`이고 총 approved/public/active POI는 305건이다. 신규 seed의 public 표시 필드와 source attribution은 한글 기준으로 보정했고, 표시 필드 영문 노출은 0건이다. 세 권역 모두 3km 10건/5km 20건 기준을 충족해 fallback gate 추가 적용 대상으로 전환한다. 서울 전체, 수도권 전체, 전국 전체 gate는 계속 적용하지 않는다.

### 리스크

- operator seed는 실제 운영 품질을 계속 확인해야 하며, 좌표 오류가 발견되면 delete가 아니라 `held` review로 public projection에서 제외한다.
- 수도권 2차 권역이 늘었지만 수도권 전체 coverage로 해석하면 안 된다.
- Kakao Local runtime은 아직 유지한다. coverage 부족 지역과 RPC error/좌표 없음/detail missing 상황에서는 fallback을 계속 허용해야 한다.

### 다음 액션

수도권 3차 coverage 후보를 준비한다. 우선 후보는 인천 송도 센트럴파크, 부천 상동호수공원, 안양·학의천/안양천, 하남·미사 후속 보강이다. 병행해서 gate 적용 권역의 Android empty UX와 fallback marker를 계속 확인한다.

  - policy evaluation recursion을 피할 수 있다.
  - plain 댓글과 reply 검증 로직을 한 함수에 모아 관리할 수 있다.

  - Supabase/PostgREST 에러는 `code/message/details/hint`를 읽을 수 있게 로깅/파싱한다.

  - `PostCard`: store를 모르는 순수 props 컴포넌트 유지

- 댓글 preview는 screen에서 전체 `commentsByPostId`를 직접 조합하지 않고, item에서 자기 `postId` 범위만 읽도록 제한한다.
- header/footer는 memoized component 수준으로 유지해 category 전환/refresh/loadMore 시 item 렌더와 같이 흔들리지 않도록 한다.
- FlatList 옵션 튜닝은 구조 분리 후 마지막에만 보수적으로 검토한다.
- 완료 기준은 아래다.
  - post 1개 좋아요 시 해당 card만 반응
  - 댓글 preview 갱신 시 해당 post card만 갱신
  - category 변경/refresh/loadMore 시 header/footer/item 영향 범위가 분리
  - 30개/100개 수준 스크롤에서 기존 대비 체감 흔들림 감소

- 댓글 row에는 author avatar를 추가했다.
  - top-level 댓글과 reply 모두 `authorAvatarUrl`이 있으면 프로필 이미지를 노출한다.
  - 이미지가 없으면 기존 `Feather user` fallback을 유지한다.
  - 구현은 `react-native-fast-image` 기준으로 맞췄고, source 객체는 `useMemo`로 고정했다.

  - 댓글 상세의 댓글 좋아요
  - 리스트의 게시글 좋아요
- 이 방식은 완전한 서버 단 debounce는 아니지만, 현재 구조를 크게 흔들지 않고도 optimistic UI를 유지하면서 API 중복 호출을 줄이는 1차 방어선으로는 충분하다.

- 커뮤니티 작성/수정 화면은 기존 `본문 + 이미지 첨부` 중심 구조였고, 서비스형 커뮤니티 기준으로는 제목 부재가 분명한 UX/데이터 계약 공백이었다.

- 이 변경은 화면만 고치면 끝나지 않는다. `CommunityCreateScreen`, `CommunityEditScreen`, `CommunityPostEditorForm`, submit shared flow, community type/service/store, 리스트/상세 소비부, 커뮤니티 SQL 문서가 함께 맞물린다.
- 현재 커뮤니티 SQL 기준 `posts.title`은 기존 문서에 없었기 때문에, 앱 코드와 함께 `커뮤니티-운영-스키마-최종.sql`, `5단계-title-컬럼-추가.sql`, 공용 초기 구성 SQL까지 같이 맞춰야 한다.
- 기존 레거시 게시글은 title이 없을 수 있으므로, 앱은 `title 미존재`를 허용하고 list/detail에서는 fallback으로 동작해야 한다.

## 1. 작업 배경

NURI는 React Native 기반의 반려동물 기억 및 메모리얼 플랫폼이다.  
다만 현재 실제 코드 기준으로 보면, 단순한 추모 전용 앱은 아니다. 반려동물별 기록, 일정, 홈 회상 허브, 날씨 및 위치 기반 행동 연결, 장소 탐색, 여행 탐색, 가이드 소비, 최소 관리자 운영 기능까지 함께 포함한 생활형 서비스 구조에 가깝다.

현재 개발 방향은 신규 기능을 무작정 넓히는 단계보다, 이미 열린 런타임 도메인을 실제 서비스 수준으로 다듬는 단계에 더 가깝다.  
즉, 현재 병목은 기능 수 부족보다는 다음 항목에 있다.

- 정합성
- 신뢰도 레이어
- 실기기 QA
- 플랫폼 완성도
- 운영 준비도

현재 코드 기준 핵심 도메인은 아래와 같다.

- 앱 부트 및 런타임 조립
- Auth 및 온보딩
- 펫 생성, 펫 프로필 수정, 멀티펫 컨텍스트
- 기록 및 타임라인
- 일정 및 기념일
- 홈 허브 및 날씨
- 주변 산책 및 위치 기반 탐색
- 펫동반 장소 탐색
- 반려동물과 여행
- 집사 꿀팁 가이드 및 관리자 기능
- 커뮤니티
- More drawer, 계정 관리, 공통 앱 구조

현재 런타임 구조를 파악할 때 우선적으로 봐야 하는 기준 파일은 아래다.

- `App.tsx`

- `src/navigation/RootNavigator.tsx`
- `src/navigation/AppTabsNavigator.tsx`

## 4. 주요 리스크

### 4.1 타입 / 정합성 리스크

- 기록 도메인은 `memory_images`와 legacy 이미지 필드를 동시에 지원한다.
- 커뮤니티는 현재 `image_url`에서 `image_urls`로 이동 중이다.
- 여러 도메인이 호환성 계층을 유지하고 있어 단기 런타임 안정성은 높지만, 장기적으로는 schema/model drift 리스크를 키운다.

### 4.2 Placeholder 노출 리스크

- Auth는 아직 소셜 로그인, 비밀번호 재설정, 정책 상세 진입을 placeholder로 노출한다.
- More drawer는 건강 기록 리포트와 알림 설정을 준비중 상태로 노출한다.
- Guestbook은 여전히 placeholder 화면이다.

### 4.3 플랫폼 리스크

- Android 일정 알림이 완전히 구현되지 않았다.
- iOS 위치 권한 처리가 서비스급 수준이 아니며 현재는 지나치게 낙관적으로 동작한다.
- Android 우선 개발 기준과 현재 플랫폼 완성도 사이에 간극이 있다.

### 4.4 외부 API 의존 리스크

- 날씨는 Open-Meteo에 의존한다.
- 산책 및 펫동반 장소 탐색은 Kakao Local에 의존한다.
- 반려동물과 여행은 TourAPI에 의존한다.
- 후보 품질과 가용성이 upstream 동작에 따라 흔들릴 수 있다.

### 4.5 Store 결합 리스크

- `AppProviders`가 여러 전역 store, boot logic, cleanup queue, session transition을 한 곳에서 조율한다.
- 현재는 동작하지만, 결합 비용이 이미 무시하기 어려운 수준이며 후속 변경 시 cross-domain 회귀 위험이 있다.

### 4.6 운영도구 부족

- 가이드 admin은 존재하지만, 전체 서비스 운영 도구는 부족하다.
- 장소 검수, 여행 trust moderation, 신고 큐 관리, cross-domain admin tooling이 여전히 비어 있다.

### 4.7 신뢰도 레이어 부족

- 펫동반 장소 trust schema는 존재하지만, 런타임 trust governance는 아직 불완전하다.
- 반려동물과 여행 Trust Layer schema는 존재하지만, 런타임은 아직 candidate-layer 중심이다.
- 따라서 앱은 유용한 결과를 보여줄 수는 있지만, 반려동물 정책 신뢰도를 강하게 보장할 수는 없다.

### 4.8 문서-코드 괴리

- 일부 오래된 커뮤니티 기획 문서는 아직 커뮤니티 미구현 전제를 갖고 있다.
- 현재 런타임 코드는 그 전제를 더 이상 따르지 않는다.
- 다음 작업자가 문서만 읽고 코드를 보지 않으면 잘못된 온보딩이 발생할 수 있다.

## 5. 검토한 선택지 / 판단

### 5.1 지금 무엇을 먼저 고도화해야 하는가

가장 적절한 근거리 우선순위는 아래다.

1. 현재 진행 중인 커뮤니티 정합성 작업을 먼저 마감한다.
2. 반려동물과 여행 Trust Layer 적용 순서와 앱 read 연결 계획을 확정한다.
3. 펫동반 장소 탐색과 반려동물과 여행에 대해 실기기 QA를 수행한다.

### 5.2 왜 이 순서가 맞는가

- 커뮤니티는 이미 현재 worktree에서 활발히 변경 중이므로, 중간 상태로 남겨두면 즉시 회귀 위험이 커진다.
- 반려동물과 여행과 펫동반 장소 탐색은 이미 사용자에게 열려 있지만, 신뢰도와 운영 기반은 약하다.
- 이 두 도메인은 기능 폭보다 신뢰도와 런타임 정합성이 다음 병목이다.

### 5.3 왜 신규 기능 추가보다 정합성 / 신뢰도 / QA가 먼저인가

- 코드베이스는 이미 다도메인 구조다.
- 여러 도메인이 기능적으로는 열려 있지만, 호환성 계층, 외부 후보 데이터, 부분적인 플랫폼 지원에 의존한다.
- 이 상태에서 기능을 더 늘리면 사용자 가치보다 유지보수 비용이 더 빠르게 증가할 가능성이 높다.
- 서비스 기준으로 보면, 현재 가장 가치 있는 작업은 런타임 동작, 저장 데이터, 문서 우선순위, 사용자 신뢰도 사이의 불일치를 줄이는 것이다.

## 6.1 추가 메모: 커뮤니티 댓글 고도화 구현 단계

이번 댓글 고도화는 단순 UI 변경이 아니라, `댓글 UI 리디자인 + 답글 데이터 구조 추가 + 성능/운영 안정화`가 같이 들어가는 작업이다.  
현재 댓글 시스템은 flat comment 기준이므로, 참고 이미지 수준의 서비스형 댓글과 답글 구조를 만들려면 단계적으로 나눠서 진행해야 한다.

### 단계 1. 댓글 UI 리디자인

목표:

- 현재 상세 화면의 댓글 row를 서비스형 대화 리스트 구조로 재배치한다.
- 카드형 느낌을 줄이고, 프로필 / 닉네임 / 날짜 / 본문 / 액션라인 구조를 정리한다.
- 광고는 범위에서 제외한다.

포함 범위:

- `CommunityDetailScreen` 댓글 리스트 레이아웃 개편
- 댓글 composer 레이아웃 개편
- 댓글 count / empty / loading / submit 상태 정리
- 댓글 더보기 버튼 위치 및 영역 정리

아직 하지 않는 것:

- 답글 저장 구조
- 댓글 좋아요
- 베스트 댓글
- 운영 배지

완료 조건:

- 현재 flat comment 구조만으로도 첫 번째 참고 이미지 수준의 서비스형 댓글 화면이 나온다.
- 댓글이 0개, 적은 글, 많은 글에서 레이아웃이 깨지지 않는다.
- Android 기준 키보드와 입력창 가시성이 유지된다.
- Android 실기기에서 키보드가 올라올 때 하단 키보드 바 / IME 영역과 composer가 겹치지 않는다.
- 키보드가 열린 상태에서도 댓글 더보기, 입력창 포커스, 제출 버튼 터치가 막히지 않는다.

### 단계 2. 댓글 데이터 모델 확장

목표:

- 답글이 가능한 1-depth 댓글 구조를 도입한다.
- 원댓글과 답글을 구분할 수 있는 source of truth를 SQL / 타입 / 서비스 / store에 만든다.

핵심 정책:

- 원댓글에는 답글을 여러 개 달 수 있다.
- 답글에도 `답글쓰기`는 가능하게 둘 수 있지만, 저장 구조는 항상 같은 원댓글 기준 `depth 1`로 평탄화한다.
- 즉, `답글의 답글`이 무한 중첩되는 구조는 허용하지 않는다.

권장 SQL 확장:

- `comments.parent_comment_id uuid null`
- `comments.depth smallint not null default 0`
- `comments.reply_count integer not null default 0`
- `comments.like_count integer not null default 0`
- `comment_likes` 테이블 추가

권장 제약:

- `depth in (0, 1)`
- `depth = 0 -> parent_comment_id is null`
- `depth = 1 -> parent_comment_id is not null`
- reply는 반드시 같은 `post_id`의 parent를 참조해야 한다

권장 인덱스:

- `(post_id, parent_comment_id, created_at asc, id asc)`
- `(parent_comment_id, created_at asc, id asc)`
- `(post_id, like_count desc, created_at asc)`
- `(user_id, created_at desc)`

완료 조건:

- 댓글과 답글을 SQL/타입/서비스/store가 모두 같은 기준으로 이해한다.
- 기존 flat comment 글도 마이그레이션 없이 정상 읽기 가능하다.

### 단계 3. 답글 UI 및 입력 흐름 연결

목표:

- 두 번째 참고 이미지 수준의 `답글쓰기`, `답글 더보기`, `parent/reply 구분` UX를 구현한다.

핵심 UX:

- top-level 댓글은 처음 10개 노출
- `댓글 더보기`는 10개 단위
- 각 댓글의 답글은 처음 최신 2개만 노출
- `답글 n개 더보기`로 확장
- composer는 기본 댓글 작성 / 답글 작성 모드를 함께 지원
- reply 작성 중에는 `OO님에게 답글 남기는 중` 상태 표시와 취소 버튼 제공

완료 조건:

- top-level / reply 구분이 시각적으로 명확하다.
- 답글 작성, 답글 취소, 답글 더보기가 모두 자연스럽게 동작한다.
- reply를 눌러도 depth 2 이상으로 저장되지 않는다.

### 단계 4. 댓글 좋아요 및 베스트 댓글 정책 적용

목표:

- 댓글 좋아요를 별도 상호작용으로 추가하고, 베스트 댓글 판단 기준을 적용한다.

초기 정책:

- 베스트 댓글은 `top-level comment`만 대상
- `comment_like_count >= 5`
- `status = active`

이유:

- 절대값이 너무 낮으면 베스트가 남발된다.
- reply까지 베스트 대상으로 넣으면 리스트가 복잡해진다.
- 초기 운영 기준으로는 `원댓글 중심 베스트`가 가장 단순하고 설명 가능하다.

완료 조건:

- 댓글 좋아요 optimistic update / rollback이 안전하게 동작한다.
- 베스트 뱃지가 과도하게 남발되지 않는다.

### 단계 5. 성능 최적화 및 리렌더링 안정화

목표:

- 댓글 수가 많아도 상세 화면 스크롤과 입력 반응이 버벅이지 않게 만든다.
- 댓글 1개 좋아요/삭제/업데이트 시 전체 화면이 흔들리지 않게 만든다.
- composer draft 상태와 댓글 list 상태의 영향 범위를 분리한다.

핵심 전략:

- `CommentThreadItem`, `ReplyCommentItem`로 댓글 렌더를 분리하고 `React.memo`를 기본으로 둔다.
- top-level/reply grouping, visible reply 계산은 pure helper 함수로 분리한다.
- screen은 orchestration만 담당하고, item은 id 또는 최소 props만 받도록 좁힌다.
- 필요 시 flat entity cache + id list 기반 normalized store 구조로 확장한다.

권장 상태 구조:

- `commentEntitiesById`
- `topLevelCommentIdsByPostId`
- `replyCommentIdsByParentId`
- `commentsStatusByPostId`
- `replyExpandedByCommentId`

렌더링 규칙:

- `renderItem` 안에서 reply grouping 계산 금지
- item 내부 store 직접 넓게 구독 금지
- selector 안에서 새 배열 / 새 객체 반환 금지
- item 컴포넌트는 id 또는 최소 primitive props 기반 memo 유지
- 좋아요 / 답글 확장 / 신고 / 삭제는 row 단위로만 갱신되게 설계
- draft 입력으로 screen이 다시 렌더돼도 comment row는 다시 그려지지 않게 유지

구현 순서:

1. `CommentThreadItem` / `ReplyCommentItem` 분리
2. `commentHelpers.ts`로 top-level/reply 파생 계산 분리
3. `CommunityDetailScreen`은 list orchestration만 남기기
4. `communityStore`는 댓글 entity/id list 구조를 도입할지 검토하고, 최소한 업데이트 범위를 row/thread 단위로 제한
5. 마지막에만 FlatList 옵션(`windowSize`, `maxToRenderPerBatch` 등) 조정 검토

완료 조건:

- 댓글이 100개 이상이어도 첫 진입과 스크롤이 급격히 무거워지지 않는다.

## 12. Android 시스템 내비게이션 바 흰색 고정

### 목표

- Android 시스템 하단 내비게이션 바(`< O □`) 배경을 `#FFFFFF`로 고정한다.
- 다크모드는 고려하지 않고, iOS는 수정하지 않는다.

### 확인 결과

- `android/app/src/main/res/values/styles.xml`
  - `AppTheme`에 `android:windowLightNavigationBar`가 이미 적용돼 있었다.
  - 이번 작업에서 `android:navigationBarColor`를 명시적 `#FFFFFF`로 통일했다.
- `android/app/src/main/java/com/nuri/MainActivity.kt`
  - 런타임에서 `window.navigationBarColor = Color.WHITE`
  - `WindowInsetsControllerCompat(...).isAppearanceLightNavigationBars = true`
  - `window.isNavigationBarContrastEnforced = false`
  기준이 이미 적용돼 있었다.
- `package.json`
  - `react-native-system-navigation-bar`
  - `react-native-navigation-bar-color`
  같은 전용 라이브러리는 설치돼 있지 않았다.

### 최종 적용 기준

- 테마 기준
  - `android:navigationBarColor = #FFFFFF`
  - `android:windowLightNavigationBar = true`
- 런타임 기준
  - `MainActivity.kt`에서 흰색 내비게이션 바와 어두운 아이콘 상태를 계속 강제 유지한다.

### 이유

- 일부 기기에서는 테마 값만으로는 하단 시스템 바 색이 일관되지 않을 수 있다.
- 화면 전환 시점에는 런타임 재적용이 없으면 기본 시스템 색으로 잠깐 돌아갈 수 있다.
- 따라서 `styles.xml + MainActivity.kt` 이중 기준으로 맞추는 편이 안정적이다.

### 추가 보강

- 현재 앱은 `targetSdkVersion = 36` 기준이라 Android 15+ edge-to-edge 강제 대상이다.
- 이 환경에서는 `navigationBarColor`만으로는 실제 기기에서 하단 시스템 바 배경이 흰색으로 유지되지 않을 수 있다.
- 그래서 `android/app/src/main/res/values-v35/styles.xml`에 `android:windowOptOutEdgeToEdgeEnforcement = true`를 추가해 Android 15+에서 시스템이 내비게이션 바 색을 무시하지 않도록 보강했다.
- 초기 시도에서 `android:windowNavigationBarColor`를 함께 넣었지만, 현재 빌드 환경에서는 존재하지 않는 style attribute로 리소스 링크가 실패해서 최종 기준에서는 제외했다.
- 일부 기기에서는 포커스 복귀 뒤 시스템 바 스타일이 다시 덮일 수 있어서, `MainActivity.kt`는 `onCreate/onResume`뿐 아니라 `onWindowFocusChanged` 시점에도 흰색 내비게이션 바 스타일을 재적용한다.

### 실제 원인 정리

- 처음에는 `styles.xml`과 `MainActivity.kt`만으로 충분하다고 봤지만, 실기기에서는 하단 시스템 바가 계속 어둡게 보였다.
- 원인은 두 가지가 겹친 상태였다.
  - `targetSdkVersion = 36` 환경의 Android 15+ edge-to-edge 강제로 인해 `navigationBarColor`가 무시될 수 있었다.
  - 화면 포커스가 돌아오는 타이밍에 시스템이 내비게이션 바 스타일을 다시 덮는데, 기존 코드는 `onCreate/onResume`까지만 재적용하고 있었다.
- 최종적으로 흰색으로 정상 복구된 기준은 아래 조합이다.
  - `styles.xml`: `windowDrawsSystemBarBackgrounds + navigationBarColor = #FFFFFF`
  - `values-v35/styles.xml`: `windowOptOutEdgeToEdgeEnforcement = true`
  - `MainActivity.kt`: `onCreate/onResume/onWindowFocusChanged`에서 `applySystemBarStyle()` 재호출

### 결론

- 이번 문제는 단순 색상값 누락이 아니라, Android 15+ 시스템 정책과 포커스 복귀 타이밍을 같이 고려하지 못해 생긴 문제였다.
- 이후 Android 시스템 바 이슈는 테마값만 보지 말고
  - target SDK
  - edge-to-edge opt-out 여부
  - Activity 포커스 복귀 시 재적용 타이밍
  를 같이 확인해야 한다.

## 13. V1.1 산책/location discovery 자체 POI read path 병행 전환

### 배경

V1.0에서는 지도/API 비용 폭탄 방어 gate를 닫았다. Google Places/Photos 경로는 차단되었고, Kakao Local은 클라이언트 직접 호출 없이 서버 경유·캐시·fan-out 제한 상태로 통제한다. 단, Kakao Local은 provider-zero가 아니므로 V1.1에서는 산책/location discovery를 자체 POI DB + Supabase PostGIS 기반 반경 검색으로 전환한다. Kakao Local은 사용자 runtime에서 제거하고, 필요 시 admin seed 보조 도구로만 제한한다.

### 결정

- 앱 산책/location discovery read path는 자체 POI public RPC를 우선 호출한다.
- 자체 POI 결과가 있으면 `walk_poi` canonical source로 표시한다.
- 자체 POI 결과가 0건이거나 RPC가 실패하면 기존 `location-discovery-seed` Edge Function + Kakao Local fallback을 유지한다.
- 이번 턴에서 Kakao Local runtime을 hard delete하지 않는다.
- canonical POI는 provider thumbnail enrichment 요청을 하지 않는다.

### RPC

- `walk_poi_public_nearby_v1`
- `walk_poi_public_search_v1`
- `walk_poi_public_detail_v1`

### 최소 seed

V1.1 Android smoke용 최소 approved operator seed 3건을 반영한다.

- 문화공원 오거리공원
- 강선공원
- 일산호수공원

seed 목적은 public RPC read path 검증이며, 전국/수도권 대량 import가 아니다. 1차 서울시청 fallback seed는 Android 실기기 현재 위치 radius 밖이라 public projection에서 제외했고, 최종 smoke seed는 일산3동/주엽동 현재 위치 기준으로 유지한다.

### admin import dry-run contract

`walk_poi_admin_import_dry_run_v1`의 payload는 source type, external id, name, category, address, 좌표, aliases, attribution, confidence/quality score, raw payload를 포함한다.

Conflict key는 `source_provider + externalSourceId`를 1순위로 두고, name/address/coordinate proximity와 alias overlap을 보조로 사용한다.

### 다음 단계

1. admin import commit/review workflow 구현
2. 자체 POI seed coverage 확대
3. Kakao Local fallback 호출량 축소 gate 정의
4. 사용자 runtime Kakao Local 제거

## 2026-07-23 자주 쓰는 기록 정렬 및 구조화 기록 필드 closeout

### 배경

홈 `자주 쓰는 기록` 카드가 1:1:1:1 한 줄 구성으로 정리된 뒤에도 카드 내부 콘텐츠의 위아래 기준선이 데이터 유무에 따라 흔들릴 수 있었고, 식사·건강·미용 요약이 제목 문자열이나 기존 감정값에 의존했다. 특히 식사 급여량과 미용 관리 항목은 실제 입력값을 보존하는 구조가 없어 홈 요약을 신뢰하기 어려웠다.

### 문제

- 카드에서 아이콘이 상단에 붙거나 요약이 바닥으로 밀리는 `space-between` 계열 레이아웃 리스크가 있었다.
- 식사 카드가 실제 급여량을 저장하지 않아 `사료 180g`을 안정적으로 파생할 수 없었다.
- 건강 카드의 컨디션·체중과 미용 카드의 관리 항목이 typed metadata로 보존되지 않았다.
- 기존 레코드에 새 값이 없어도 이전 데이터가 깨지지 않아야 했다.

### 검토한 선택지

1. 홈 카드에 값을 하드코딩한다.
2. 제목·내용 문자열을 계속 파싱한다.
3. 기존 `memories`와 `pets`에 backward-compatible nullable/JSON 구조를 추가하고, 입력 화면과 홈 selector가 같은 계약을 사용한다.

### 최종 결정과 이유

세 번째 방식을 적용했다. `memories.metadata jsonb not null default '{}'`에 버전 1 metadata를 저장하고, `pets.default_meal_amount_grams numeric(7,2)`에 반려동물별 기본 급여량을 저장했다. 기존 레코드는 빈 metadata로 그대로 읽히며, RLS와 기존 사용자·펫 scope를 유지한다. 홈은 선택된 펫의 최신 레코드만 사용한다.

### 데이터 구조

- 식사: `metadata.meal.foodType`, `metadata.meal.amountGrams`
- 건강: `metadata.health.condition`, `metadata.health.weightKg`
- 미용: `metadata.grooming.careTypes[]`
- 기본 급여량: `pets.default_meal_amount_grams`, null은 미설정
- migration: `supabase/migrations/20260723110000_record_structured_fields.sql`

### 카테고리별 요약 규칙

- 산책: 실제 `createdAt`을 기기 로컬 시간으로 변환해 05:00~10:59 오전, 11:00~13:59 점심, 14:00~17:59 오후, 18:00~21:59 저녁, 그 외 밤으로 표시한다. 무효 시각은 `산책 기록 완료`다.
- 식사: 음식 종류와 양이 있으면 `사료 180g`, 양만 있으면 `180g 급여`, 둘 다 없으면 `식사 기록 완료`다. 이번 입력 화면은 현재 서비스 계약을 유지해 사료를 기본 음식 종류로 저장한다.
- 건강: 컨디션과 체중이 모두 있으면 `지켜봐야 해요 · 4.8kg`, 컨디션만 있으면 컨디션 문구, 체중만 있으면 체중 문구를 표시한다.
- 미용: 전체 미용은 단독 표시하고, 1개는 항목명, 2개는 `항목 & 항목`, 3개 이상은 `첫 항목 외 N개`로 표시한다. 전체 미용과 세부 항목은 상호 배타적이다.

### 식사 기본 급여량 동작

기본값은 선택된 펫 단위로 서버에 저장한다. 기본값이 있으면 다음 식사 화면에서 자동 입력·체크되며, 체크를 해제하면 이번 식사만 수동 급여량을 입력할 수 있다. 최초 기본값이 없으면 입력한 급여량을 기본값으로 저장할 수 있다. 급여량은 0 이하·빈 값·비정상 숫자를 저장하지 않는다.

### 리스크

- 이번 migration은 additive이며 기존 metadata가 없는 레코드의 fallback을 유지한다.
- `createdAt`이 실제 수행 시각을 별도 보존하지 않는 기존 구조이므로 산책 시간대는 현재 서비스의 생성 시각 기준이다.
- 새로운 최종 QA 기록은 운영 데이터가 아닌 고정 QA 계정에만 남겼다.

### 검증 결과

- Android `SM_S937N / R5CY613NMSY`, 고정 `adminQA`와 기존 QA 펫에서 산책·식사 180g/150g·건강 컨디션/4.8kg·미용 목욕/털 정리 실제 저장을 완료했다.
- 저장 직후 홈 요약, 앱 강제 종료 후 재실행 영속성을 확인했다.
- 1:1:1:1 카드의 수직 중앙 정렬과 60초 상대시간 갱신 계약을 확인했다.
- `corepack yarn tsc --noEmit --pretty false`, `corepack yarn lint`, focused 8 tests, 전체 Jest 69 suites / 277 tests, release build/install, Supabase dry-run을 통과했다.

# NURI 전체 타이포그래피·레이아웃·카드 구조 기준선 조사 및 메인 홈 정리

## 1. 배경

이번 조사는 NURI 앱 전체에 공통으로 적용할 최종 글자 크기, 굵기, 간격, 카드 반지름을 바로 바꾸기 위한 작업이 아니다. 현재 실제 코드에 흩어진 typography, spacing, borderRadius, shadow 기준을 먼저 수집하고, 사용자가 지정한 메인 홈 세 항목만 최소 범위로 구현하기 위한 기준선 조사다.

조사 대상은 실제 소스 기준 비커뮤니티 303개 JavaScript/TypeScript 소스 파일, 화면 디렉터리 19개, 커뮤니티를 제외한 화면 파일 74개다. root 및 nested navigator에서 확인한 고유 route 이름은 52개다. 일반 Modal, DatePicker, TimePicker, Alert, Portal 계열은 커뮤니티를 제외하고 33개 파일에서 확인했다.

조사에서 커뮤니티 전체와 앱 하단 네비게이션은 존재 여부와 공유 관계만 확인하고, 이번 typography·spacing·radius 변경 대상에서 제외했다. 앱의 실제 폰트 자산은 Android assets와 앱 assets에 있는 PretendardVariable.ttf다.

## 2. 문제

- semantic typography token은 존재하지만 화면별 StyleSheet에 직접 지정한 값도 많이 남아 있다.
- 비커뮤니티 영역에서 확인된 fontSize 고유값은 27개, fontWeight 고유값은 14개, lineHeight 고유값은 29개, letterSpacing 고유값은 13개다.
- paddingHorizontal 고유값은 25개, paddingVertical은 23개, gap은 20개, borderRadius는 40개다.
- 가장 많이 쓰이는 글자 크기는 12, 13, 16, 14, 11 순서이며, 8부터 76까지의 값과 조건부 계산값이 함께 존재한다.
- fontWeight는 400, 500, 600, 700, 800, 900과 조건부 weight 표현이 함께 존재한다. 900이 가장 많이 쓰여 semantic token의 extrabold 800과 화면 코드의 강한 강조 900이 혼용된다.
- 화면 좌우 padding과 카드 내부 padding이 중첩되는 화면이 있어 긴 한글 문구가 두 줄로 내려갈 수 있다.
- 일부 섹션은 외부 카드, 내부 카드, border, shadow, gradient, 큰 radius가 동시에 적용돼 정보 계층보다 장식이 먼저 보일 위험이 있다.
- 기존 최근 기록은 기록 항목마다 radius, background, border, shadow를 가진 독립 카드였다. 동일한 리스트 안에서 카드가 반복되어 화면이 조각나고, 날짜 그룹과 기록 행의 구분이 중복됐다.
- 로그인 홈의 HeroProfileMessage와 헤더의 정적 `오늘의 메시지로 하루를 시작해요` 문구는 현재 선택된 반려동물과 사망일을 기반으로 한 오늘 메시지 영역과 목적이 겹쳤다. 이번 홈 정리 범위에서는 두 로그인 홈 경로를 제거했다. GuestHome이 같은 스타일 계약을 공유하므로 공용 스타일은 삭제하지 않았다.
- 자주 쓰는 기록의 상대시간 pill에는 시계 아이콘이 있었고, 사용자는 날짜·시간 텍스트만 남기기를 요청했다.

## 3. 선택지

1. 이번 턴에 전역 typography, spacing, radius를 일괄 변경한다.
2. 공통 Text/Card 토큰을 먼저 전면 교체한다.
3. 전체 기준선을 조사 문서에 고정하고, 명시된 메인 홈 세 항목만 화면 로컬 변경으로 닫는다.
4. 최근 기록의 기존 항목 카드만 약간 줄이고 외부 컨테이너는 두지 않는다.

## 4. 결정 이유

세 번째 선택지를 적용했다. 사용자는 아직 NURI 전체에 적용할 최종 fontSize와 fontWeight를 확정하지 않았고, 공통 컴포넌트는 GuestHome, 다른 기록 화면, 커뮤니티 또는 navigation과 공유될 가능성이 있다. 따라서 전역 변경은 이번 턴에서 하지 않는다.

이번 턴의 실제 코드 변경은 다음 세 가지로 제한했다.

- 로그인 홈의 HeroProfileMessage, todayMessage 계산, 헤더의 정적 오늘 메시지 문구와 로그인 홈 전용 render 전달을 제거했다. homeRecall 서비스 자체와 GuestHome의 메시지 경로는 유지했다.
- 자주 쓰는 기록의 clock 아이콘만 제거하고 relative time 계산, pill 텍스트, 카드 진입 동작은 유지했다.
- 최근 기록을 단일 외부 카드로 감싸고 기록 항목은 row로 유지했다. row에는 개별 radius, background, border, shadow, elevation을 제거하고 마지막 행을 제외한 행에 텍스트 시작점 기준 inset divider를 추가했다. 로딩과 빈 상태도 동일 외부 카드 안에 두어 중첩 카드가 생기지 않게 했다.

Naver/Apple 로그인 잔존 여부는 조사했으나 이번 턴에서 수정하지 않았다.

## 5. 리스크

- 공통 AppText와 화면별 StyleSheet를 함께 전역 수정하면 모달·입력·GuestHome까지 회귀할 수 있다.
- GuestHome은 LoggedInHome.styles.ts의 heroMessage 스타일을 공유하므로 로그인 홈 메시지 제거 시 공용 스타일을 삭제하면 게스트 화면이 깨진다.
- 최근 기록 row는 기존 상세 route, accessibility label, 날짜 formatter, selector를 유지해야 하며 외부 카드만 바꾸는 것이 안전하다.
- 작은 화면과 시스템 fontScale에서 긴 한글 제목·요약·날짜가 다시 줄바꿈될 수 있다. 현재 실기기는 384dp 논리 폭이므로 360dp 기기 별도 증적은 없다.
- 현재 실기기 모델은 adb 식별값 SM-S937N이다. 사용자가 말한 Galaxy S24 기준과 실제 모델명이 일치하지 않으므로 이번 보고서는 실제 모델명을 source of truth로 기록한다.
- 정적 인벤토리의 고유값은 선언 기준이며 runtime에서 조건부로 조합되는 StyleSheet 값까지 하나의 token으로 해석해서는 안 된다.
- 커뮤니티와 navigation은 공유 컴포넌트 영향 때문에 이번 턴에서 변경하지 않았다.
- 오늘의 명언 데이터 서비스 homeRecall 자체를 삭제하지 않아, 다른 화면 또는 GuestHome에서 계속 사용할 수 있다. 이는 미사용 코드 정리가 아니라 공유 계약 보존을 위한 의도적 유지다.
