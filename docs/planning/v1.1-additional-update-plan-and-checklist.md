## 0. 문서 목적

이 문서는 PO가 제안한 V1.1 추가 업데이트 후보 8개를 실제 구현 착수 전에 공식 작업 단위로 고정하기 위한 planning source of truth다.

## 3. 단계별 구현 계획

### 3-1. 1차 MVP

목표: 위험도가 낮고 앱 완성도와 계정 안전에 직접 기여하는 기능을 먼저 닫는다.

1. 회원 탈퇴 시 “회원탈퇴” 직접 입력 확인
2. 최근 로그인 방식 표시
3. 타임라인 카테고리별 게시물 개수 표시

1차 MVP 완료 조건:

- 기존 Auth/Account/Timeline 계약을 깨지 않는다.
- 신규 migration은 필요할 때만 별도 승인 후 생성한다.
- Android 실기기에서 회원 탈퇴 취소/요청, 로그인 방식 표시, 타임라인 count 표시를 확인한다.
- typecheck, lint, focused test, navigation/back smoke를 통과한다.

### 3-2. 2차 MVP

목표: 리텐션 기능의 최소 계약을 만든다.

1. 산책·타임라인 활동 기반 연속 출석/데일리판
2. 로그인 후 홈 알림 badge/read path 검증
3. 활동 XP/칭호 정책표와 최소 MVP

2차 MVP 완료 조건:

- streak와 XP 지급 기준이 PO 확정된 상태여야 한다.
- abuse 방지를 위해 하루 인정 횟수와 중복 지급 방지 기준을 포함한다.
- 알림은 앱 내부 read path부터 확인하고, 운영자 발송 페이지와 push는 별도 트랙으로 둔다.

### 3-3. 3차 / V1.1.1 후보

목표: 운영 정책과 감성 문구 검수가 필요한 기능을 별도 안정화 단위로 분리한다.

1. 무지개다리 상태 전환 후 추억 서비스 문의
2. Android 홈 위젯 1차
3. XP/레벨/칭호 전체 시스템
4. 운영자 알림 발송 관리 페이지
5. 푸시 알림

3차/V1.1.1 완료 조건:

- 감성 문구, 노출 빈도, 거부/닫기 동선이 PO 확정되어야 한다.
- 운영자 발송 기능은 앱 내부 admin이 아니라 별도 홈페이지/관리 페이지 트랙에서 다룬다.
- 푸시 알림은 동의, opt-out, abuse 방어, delivery log 정책 확정 후 진행한다.

### 3-4. 출시 후 고도화

1. 실제 앨범/영상 상품 결제
2. iOS 위젯
3. 고급 칭호/랭킹/뱃지 시스템
4. 자동 영상 생성
5. 운영자 관리 페이지 고도화

## 4. 기능별 상세 기획

### 4-1. 타임라인 카테고리별 게시물 개수 표시

- 목적: 타임라인 사용자가 기록 분포를 빠르게 파악하게 한다.
- 사용자 가치: 산책, 건강, 일상 등 기록 습관이 화면에서 즉시 보인다.
- 구현 범위: 타임라인 카테고리 탭 또는 요약 영역에 카테고리별 count 표시.
- 제외 범위: 랭킹, XP, 배지, 통계 상세 화면.
- 권장 UX: 현재 타임라인 IA를 유지하고 count만 보조 정보로 추가한다.
- 데이터/RPC 필요 여부: 기존 타임라인 query에서 count가 충분한지 확인 후, 부족하면 read-only summary RPC를 별도 설계한다.
- 예상 수정 영역: Timeline screen, timeline hook/store, 필요 시 Supabase read summary.
- 난이도: 낮음.
- 위험도: 낮음. count와 실제 리스트 필터가 어긋나면 신뢰도 문제가 생긴다.
- 우선순위: 1차 MVP.
- 예상 테스트: 카테고리별 count, empty category, 작성 후 count 갱신, Android back.
- release blocker 가능성: 낮음.
- PO 확정 필요 여부: 낮음. 표시 위치만 확정 필요.
- 진행률 산정 기준: 정책 10%, 데이터 확인 15%, UX 설계 15%, 구현 30%, 테스트 20%, 문서/evidence 10%.
- 완료 조건: 카테고리 count가 실제 리스트 기준과 일치하고 Android smoke를 통과한다.

### 4-2. 최근 로그인 방식 표시

- 목적: 사용자가 어떤 방식으로 로그인했는지 계정 화면에서 확인하게 한다.
- 사용자 가치: 재로그인, 계정 관리, 문의 대응이 쉬워진다.
- 구현 범위: 계정/설정 화면에 최근 로그인 방식 표시.
- 제외 범위: provider 변경, 연결 해제, multi-provider link.
- 권장 UX: 이메일, Google, Kakao처럼 사용자가 이해하는 한글 라벨로 표시한다.
- 데이터/RPC 필요 여부: Supabase session/provider metadata 또는 app auth state에서 안전하게 파생 가능한지 확인한다. 필요 시 profile snapshot은 별도 승인 후 설계한다.
- 예상 수정 영역: Auth store, account/settings screen, auth utility.
- 난이도: 낮음.
- 위험도: 낮음. provider metadata 누락 시 안전한 “확인 중” 표시가 필요하다.
- 우선순위: 1차 MVP.
- 예상 테스트: email/password, Google, Kakao, 로그아웃 후 복귀.
- release blocker 가능성: 낮음.
- PO 확정 필요 여부: 표시 문구만 확정 필요.
- 진행률 산정 기준: 정책 10%, 데이터 확인 20%, UX 설계 10%, 구현 30%, 테스트 20%, 문서/evidence 10%.
- 완료 조건: 로그인 방식이 과장 없이 표시되고 소셜 로그인 동작에 영향이 없다.

### 4-3. 무지개다리 상태 전환 시 추억 상품/서비스 제안

- 목적: 반려동물 상태 전환의 민감한 순간에 추억 보관 서비스를 조심스럽게 안내한다.
- 사용자 가치: 사용자가 원할 때 추억 상품/서비스 문의 경로를 찾을 수 있다.
- 구현 범위: 상태 전환 완료 후 1회성 조심스러운 안내 또는 문의 진입.
- 제외 범위: 결제, 상품 주문, 자동 업셀, 반복 팝업.
- 권장 UX: 닫기 쉬운 안내, 한 번만 노출, 다시 보기 경로는 설정/프로필에 둔다.
- 데이터/RPC 필요 여부: 노출 이력 저장이 필요하다. 결제/주문 테이블은 이번 범위에서 제외한다.
- 예상 수정 영역: Pet status update flow, profile/pet state, optional notice log.
- 난이도: 중간.
- 위험도: 높음. 감성 문구와 노출 타이밍이 부적절하면 신뢰를 해친다.
- 우선순위: V1.1.1 후보.
- 예상 테스트: 상태 전환, 안내 1회 노출, 닫기, 재진입 시 미노출, Android back.
- release blocker 가능성: 중간. 문구/노출 정책 미확정 시 blocker로 승격될 수 있다.
- PO 확정 필요 여부: 높음.
- 진행률 산정 기준: PO 문구/정책 20%, 데이터 설계 15%, UX 설계 20%, 구현 20%, 테스트 15%, 문서/evidence 10%.
- 완료 조건: 민감 상태 전환 UX가 안전하고 반복 노출/강매 느낌이 없다.

### 4-4. 산책·타임라인 활동 기반 연속 출석/데일리판

- 목적: 일일 기록 습관을 만들고 앱 재방문을 유도한다.
- 사용자 가치: 오늘의 산책/기록 여부와 연속 활동을 확인할 수 있다.
- 구현 범위: 산책 또는 타임라인 활동을 기준으로 일간 streak count와 데일리판 표시.
- 제외 범위: 보상 경제, 랭킹, 고급 배지.
- 권장 UX: 홈 또는 타임라인 인접 영역에 작은 상태 표시부터 시작한다.
- 데이터/RPC 필요 여부: activity event summary 또는 기존 write path 기준의 read summary가 필요할 수 있다.
- 예상 수정 영역: Timeline, Walk activity read path, Home summary, activity summary service.
- 난이도: 중간.
- 위험도: 중간. 인정 기준이 모호하면 사용자 불만과 abuse가 생긴다.
- 우선순위: 2차 MVP.
- 예상 테스트: 오늘 활동 있음/없음, 연속일 갱신, 날짜 경계, 중복 방지.
- release blocker 가능성: 낮음. 단, 기존 timeline/walk write path를 건드리면 중간으로 상승한다.
- PO 확정 필요 여부: 높음.
- 진행률 산정 기준: PO 인정 기준 15%, 데이터 설계 20%, UX 설계 15%, 구현 25%, 테스트 15%, 문서/evidence 10%.
- 완료 조건: 인정 기준이 명확하고 중복 count 없이 Android smoke를 통과한다.

### 4-5. 홈 위젯: 우리 아이와 함께한 시간, 날짜, 날씨, 앱 진입

- 목적: 앱 밖 또는 홈 진입점에서 반려동물과 함께한 시간을 노출한다.
- 사용자 가치: 앱 재방문 이유가 생기고 날씨/날짜 정보와 연결된다.
- 구현 범위: 1차는 앱 내부 홈 카드 또는 Android 위젯 중 PO가 선택한 범위만 진행.
- 제외 범위: iOS 위젯, 여러 디자인 variation, 고급 personalization.
- 권장 UX: 스토어 출시 전 디자인 조정 트랙과 충돌하지 않게 범위를 확정한다.
- 데이터/RPC 필요 여부: 함께한 날짜 기준, 날씨 cache read path, pet profile read path 확인 필요.
- 예상 수정 영역: Home summary, weather preview, Android widget module if selected.
- 난이도: 중간~높음.
- 위험도: 중간. Android native widget을 열면 빌드/권한/디자인 QA가 늘어난다.
- 우선순위: V1.1.1 후보.
- 예상 테스트: 날짜 계산, 날씨 표시, 앱 진입 deep link, Android cold start.
- release blocker 가능성: 중간. native widget 범위일 때 release risk가 올라간다.
- PO 확정 필요 여부: 높음.
- 진행률 산정 기준: PO 플랫폼/날짜 기준 15%, 데이터 설계 15%, UX 설계 20%, 구현 25%, 테스트 15%, 문서/evidence 10%.
- 완료 조건: 함께한 날짜 기준이 확정되고 앱 진입/날씨 표시가 crash 없이 동작한다.

### 4-6. 회원 탈퇴 시 “회원탈퇴” 직접 입력 확인

- 목적: 실수 탈퇴를 줄이고 계정 삭제 의사 확인을 강화한다.
- 사용자 가치: 되돌리기 어려운 계정 조작 전에 명확한 확인 단계를 거친다.
- 구현 범위: 탈퇴 요청 전 “회원탈퇴” 직접 입력 modal 또는 confirmation step.
- 제외 범위: 7일 유예 정책 변경, hard delete timing 변경, 복구 정책 변경.
- 권장 UX: 입력 전에는 탈퇴 요청 버튼 비활성, 취소/닫기/Android back은 안전하게 복귀.
- 데이터/RPC 필요 여부: 기존 탈퇴 RPC 유지. 신규 DB 필요 없음.
- 예상 수정 영역: Account deletion UI, form state, focused tests.
- 난이도: 낮음.
- 위험도: 낮음. 기존 탈퇴 flow가 깨지면 release blocker가 될 수 있다.
- 우선순위: 1차 MVP.
- 예상 테스트: 잘못된 입력, 정확한 입력, 취소, Android back, 7일 유예 요청.
- release blocker 가능성: 중간. 계정 삭제는 core account safety다.
- PO 확정 필요 여부: 낮음. 입력 문구는 “회원탈퇴”로 확정.
- 진행률 산정 기준: 기존 탈퇴 flow 20%, UX 설계 10%, 구현 30%, 테스트 30%, 문서/evidence 10%.
- 완료 조건: 입력 확인이 없으면 요청 불가하고 기존 7일 유예/복구 계약이 유지된다.

### 4-7. 운영자/계정 알림 발송 및 로그인홈 알림 수신 검증

- 목적: 계정 단위 안내와 운영 공지를 앱에서 안전하게 수신한다.
- 사용자 가치: 중요한 계정 상태와 공지를 놓치지 않는다.
- 구현 범위: 2차 MVP는 로그인 후 홈/전체메뉴에서 앱 내부 알림 read path와 badge를 검증한다.
- 제외 범위: 앱 내부 admin 발송 UI, 별도 홈페이지 관리 페이지, push notification.
- 권장 UX: 일반 사용자는 알림 수신/읽음 처리만 본다. 발송은 별도 관리 페이지 트랙에서 다룬다.
- 데이터/RPC 필요 여부: user notification table/RPC 또는 기존 알림 구조 확인 필요.
- 예상 수정 영역: notification read model, Home/LoginHome badge, settings/menu entry.
- 난이도: 중간.
- 위험도: 중간. 운영자 발송과 사용자 수신 권한 경계를 잘라야 한다.
- 우선순위: 2차 MVP.
- 예상 테스트: 알림 없음, 알림 있음, 읽음 처리, 일반 사용자 admin 미노출.
- release blocker 가능성: 낮음. 단, 권한 누수는 blocker다.
- PO 확정 필요 여부: 높음.
- 진행률 산정 기준: 알림 범위 정책 15%, 데이터/RPC 설계 25%, UX 설계 10%, 구현 25%, 테스트 15%, 문서/evidence 10%.
- 완료 조건: 일반 사용자는 알림을 읽을 수 있고 운영자 발송 기능은 앱 내부에 열리지 않는다.

### 4-8. 활동 경험치·레벨·칭호 시스템

- 목적: 건강한 기록 활동을 장기 리텐션으로 연결한다.
- 사용자 가치: 활동 누적이 눈에 보이고 반려동물과의 기록 동기가 생긴다.
- 구현 범위: 최소 MVP는 XP 정책표, 서버 지급 계약, 기본 레벨/칭호 표시.
- 제외 범위: 랭킹, 경쟁형 보상, 결제 보상, 고급 뱃지.
- 권장 UX: 경쟁보다 기록 격려 톤으로 시작한다.
- 데이터/RPC 필요 여부: activity ledger, XP event, level/title snapshot 또는 read summary가 필요하다.
- 예상 수정 영역: activity write paths, profile/home summary, XP policy service, tests.
- 난이도: 높음.
- 위험도: 높음. abuse 방어, 중복 지급, 소급 계산 기준이 없으면 운영 비용이 커진다.
- 우선순위: 2차 MVP 설계, V1.1.1 확장.
- 예상 테스트: XP 지급, 하루 제한, 중복 방지, 레벨 상승, 칭호 표시, rollback-like recompute policy.
- release blocker 가능성: 중간. 기존 write path에 영향을 주면 높아진다.
- PO 확정 필요 여부: 높음.
- 진행률 산정 기준: XP/칭호 정책 15%, 데이터/RPC 설계 20%, UX 설계 10%, 구현 30%, abuse/test 15%, 문서/evidence 10%.
- 완료 조건: 지급 기준과 제한이 서버 계약으로 안전하게 고정되고 Android smoke를 통과한다.
