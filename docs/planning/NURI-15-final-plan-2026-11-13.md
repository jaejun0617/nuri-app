# NURI-15 공지사항·고객센터 최종 기획

2026-11-13 KST · **기획 완료 / 후속 승인에 따른 개발 UI 착수 / 운영 공개 미승인**

### 후속 구현 범위

**11/14 PO 후속: 문의 글 등록과 공통 UI.** 고객센터의 문의하기 → 기존 문의 유형 선택 → 문의하기 CTA → 제목·본문·사진을 갖춘 문의 글 등록으로 진입한다. 선택한 유형은 등록 화면의 아코디언에 이어받고 그 안에서 변경할 수 있다. 긴 유형을 칩으로 바꾸거나 첫 유형 선택을 제거하지 않는다. 제목은 1~80자, 본문은 기존 2,000자, 사진은 기존 최대 3장 계약이다. 제목과 유효 본문 또는 준비된 사진으로 접수한다. 기존 제목 없는 문의·사진만 첫 접수의 역사 증거는 그대로 보존하며 새 등록 계약의 제목을 임의 생성해 backfill하지 않는다. U06의 작성 전 채팅형 설명은 이 후속 지시로 대체하고 접수 후 동일 문의방·추가 질문·답변은 유지한다. U07과 관리자 큐는 제목을 먼저 보여주고 유형·시각을 함께 표시한다.

- 등록 표면은 `Glass`가 감싼 `HomeReflectiveGlass`, 등록 버튼은 `CtaButton`·`CtaText`를 재사용한다. [공통 글라스·CTA 상시 기준](../project-memory/핵심-결정사항.md#shared-glass-cta-required)을 따른다.
- 실제 로컬 Auth/API를 통한 새 등록·중복 요청·권한 검사와 독립 답변 worker를 연결했다. 공용 알림의 행·그룹·읽음 표현을 공유하고 알림함의 DEV 격리 진입에서 해당 문의방을 연다. **운영 `user_notifications` 원장 병합·resolver·OS push 연결은 아직 아니다.** 화면 공유와 운영 backend 통합을 구분한다.
- [11/14 실행 기록](../project-memory/최근-작업-로그.md#nuri-15-registration-independent-worker)은 S25 Edge Metro 개발 확인이며 새 Metro OFF/Release 수락이 아니다. 아래 초기 기획과 11/13 관찰은 당시 이력으로 보존한다.

**11/13 콘텐츠·관리 후속:** 개발 화면의 공지 5개와 FAQ 10개는 현재 기능 기준 원고이며 운영 게시가 아니다. 공지 상세와 문의 내역에 KST 시·분을 표시하고, 공지 상세에는 누리 장식을 사용한다. 전체메뉴 구독 진입은 하나이며 왕관 배지는 현재 DEV 메뉴·세션의 모의 구독만 나타낸다. 앱 소유 확인창은 누리 공통 모달을 사용한다.

**앱 신고 처리와 삭제의 경계:** 관리자 신고 목록·상세에서 검토 상태와 메모를 저장한다. `처리 완료`는 신고 검토 종료일 뿐 게시글이나 댓글의 숨김·삭제가 아니다. 정책 위반을 확정한 경우에만 권한 있는 관리자에게 별도의 명시적 `게시글 삭제` 명령을 제공하는 안을 채택한다. 공개 목록과 상세에서 내리고 원본은 감사·이의제기 기간에 한해 비공개로 보존한다. 보존기간·영구 정리, 신고 접수의 관리자 알림과 자동 처리는 별도 운영 계약이다. 자동화가 추가되더라도 동일한 권한·감사·중복 방지 경계를 거쳐야 하며 신고 접수나 검토 상태만으로 삭제하지 않는다. 이번에는 삭제 명령과 자동화를 구현하거나 실행하지 않는다.

**11/13 후속 앱 연결:** 별도 개발 화면의 실제 격리 Auth 및 공지 API로 앱 작성·게시·일반 사용자 목록·정확한 상세·표시 후 서버 읽음·헤더/Android Back을 연결했다. S25 Edge Metro 한정이며 운영 연결·Metro OFF·Release 전체 수락은 아니다. 기존 공지/읽음·비교 계정·outbox 불변 근거와 입력 중 네이티브 종료의 미해결 한계는 [후속 실행 로그](../project-memory/최근-작업-로그.md#2026-11-13-nuri-15-격리-공지-앱-연결)가 소유한다. 아래의 '앱 미연결'은 이 실행 전 시점이다.

**PO 추가 확정 요구:** 전체메뉴 공지사항과 커뮤니티 공지사항은 일반 사용자에게 글등록·수정·삭제 버튼을 노출하지 않으며 직접 API 요청도 서버에서 거부한다. PO가 지정한 관리자 계정으로 작성 화면을 통해 등록·수정·삭제할 수 있어야 한다. 전체 이메일은 공개 문서에 복제하지 않는다. PO의 Supabase 슈퍼어드민 설명과 앱의 검증된 서버 capability는 구분하며, 이메일/클라이언트 metadata만으로 권한을 부여하지 않는다. 기존 커뮤니티 moderation·감사 계약을 유지하고 두 게시판을 임의 동기화하지 않는다. **삭제 설계 권고:** 사용자 목록/상세에서 제거하되 감사·원본 보존 규칙을 유지하는 논리 삭제를 기존 게시 중단(재게시 가능)과 별도로 명세한다. 영구 DB 삭제나 기존 글 일괄 삭제는 이 요구의 자동 실행 범위가 아니다. 이번 앱 연결은 신규 작성·게시까지만 구현/검증했으며 기존 글 수정·삭제와 커뮤니티 연결은 잔여다.

**11/13 후속 실행 증분:** 구독·공지·고객센터 배경과 글라스를 전체메뉴의 공통 컴포넌트에 맞췄다. 관리자 화면은 로컬 UI로 추가했다. 새 로컬 격리 환경 재구성 승인에 따라 별도 Auth/API/DB에서 게시판·텍스트 문의 정의를 적용하고 실제 API 25개와 SQL 계약 31개를 확인했다. 앱 화면은 아직 이 API를 소비하지 않으며 첨부·FAQ 서버·알림 전달·재접속과 설치본 수락은 남아 있다. 아래 초기 기획 당시 NOT RUN과 구분하며 QA01~QA36·PV01 전체를 새 PASS로 바꾸지 않는다. [환경·검증·정확한 잔여](../project-memory/최근-작업-로그.md#2026-11-13-nuri-15-격리-서버와-공통-표면).

**11/13 후속 PO 표시 변경:** 개발 중 서비스와 같은 화면 확인을 위해 화면의 미리보기·실결제/접수 미실행 안내와 예시 접두어를 제거했다. 개발용 잠정 가격은 메모리 월 4,900원·연 49,000원, 플러스 월 7,900원·연 79,000원이다. 가격은 코드 내 로컬 카탈로그이며 판매가격 확정이나 Store 상품 등록이 아니다. 아래 이전 PV01의 가상 거래 식별 문구와 C03 표시 요구는 이번 개발 화면에 한해 이 지시로 대체한다. 실제 서버·결제 비연결, DEV 한정 진입, 세션 격리와 Release 진입 차단 수락 조건은 유지한다. 운영 연결 전 요금·상품·영수증·공개 범위를 다시 확정한다.

후속 PO 지시로 디자인을 먼저 구현했다. 아래 기획 조사·검수의 관찰 시점과 QA01~QA36·PV01의 최종 수락 상태는 변경하지 않는다. 현재 개발 화면은 전체메뉴의 이용 안내(공지사항·고객센터), 계정(구독하기)에서 진입하며 별도 ‘디자인 미리보기’ 메뉴 묶음은 만들지 않는다. `src/screens/Support/`의 화면 로컬 예시로 구성했고 문의·결제·첨부·권한·발송 서버 연결은 아직 없다.

활동·칭호의 AppText 및 ACTIVITY_READING_TYPE을 재사용한다. 사용자 NURI 시안의 헤드셋·확성기·말풍선·봉투는 원본 PNG를 보존한 클리핑 이미지 레이어로 적용하며 텍스트·입력·버튼은 실제 컴포넌트다. 독립 투명 장식 원본을 확보한 것은 아니다. 타 앱 참조는 요금 선택·비교·하단 CTA 구성만 반영하고 가격·평점·회원 수를 NURI 사실로 복제하지 않는다. 로컬 모의 구독은 닫기·재진입 시 초기화되고 실제 entitlement·주문·문의 배지와 연결되지 않는다. 개발 메뉴·모달 가드 및 route 미등록을 검사했으나 실제 Release 후보의 모든 진입 경로 차단은 아직 NOT RUN이다.

S25 Edge의 Metro 개발 화면에서 메뉴·고객센터 이미지·구독 전환·배지를 관찰했다. 독립 APK의 최종 수락이 아니며 관리자 UI·서버 기능·전체 화면 상태 검증까지 완료한 것은 아니다. [후속 기록](../project-memory/최근-작업-로그.md#2026-11-13-nuri-15-디자인-우선-구현)에서 검사·한계를 구분한다.

## 1. 배경

- **PO 확정 요구:** 사용자와 운영자가 같은 NURI 앱을 사용한다. 운영자는 앱에서 공지를 작성·수정·중단하고 문의에 답한다. 일반 사용자는 운영 메뉴를 보지 않으며, 숨김과 별개로 서버가 권한을 검사한다. 별도 웹 관리 화면은 선행 조건이 아니다. 첨부 시안을 기준으로 하고 내 문의 내역 등 없는 화면은 같은 디자인 언어로 설계한다.
- **PO 후속 지시:** 구독 취소·환불은 실결제 연동 전에 화면부터 준비한다. 전체메뉴 상단 닉네임·펫 정보의 구독자 스타일은 개발 전용 버튼으로 비교한다. 이번 차수에는 둘 다 명세만 반영한다. 화면 선제작은 운영 노출·결제 활성화·환불 실행을 승인하지 않는다.
- **현재 재확인:** Master `codex/walk-marker-recovery-20261020`, HEAD `272d576`과 기존 작업 트리. 첨부한 「공지사항 과 고객센터 최종 기획안」(내부 제목 「NURI-15 공지사항과 고객센터 최종 기획 보완안」, 738행, SHA-256 `fb4fff63a004f883d4c16fe446e8a332c3b17b0998c6f2bc24b9542cd80d8628`)과 사용자 시안 10장 확인. 소스·테스트 정의·연결 프로젝트의 catalog 및 bucket metadata만 읽었다. 실제 데이터·문의·거래·사용자 행은 조회하지 않았다.
- **자료 식별 정정:** Master는 위 738행 보완안의 본문을 직접 읽었다. 이번 전달 검수 자료는 해당 해시가 보관된 `NURI-15-final-plan-2026-11-11.md`의 실제 바이트 해시와 동일하다고 확인했다. 이는 전달 자료의 동일성 확인이며 Master가 독립 파일을 새로 찾아 직접 해시를 대조한 것은 아니다. 저장소·관련 자료에서 특정 이름의 독립 파일을 찾지 못한 관찰과 별개로 동일 본문의 열람은 유지하며 재탐색을 완료 조건으로 두지 않는다.
- **별도 원보고서 한계:** 보완안에 인용된 「NURI-15 전체메뉴 공지사항·고객센터 구현 기획 보고서」의 Library 링크는 본문을 반환하지 않아 직접 열람하지 못했다. 보완안의 원문 인용과 당시 SHA는 역사 근거다. 이 문서 한 건을 정본으로 유지하고 원본·이미지는 수정하지 않는다. 시안 10장 확인과 독립 장식 원본 미확인은 §4.1대로 보존한다.
- **검수 반영 시점:** 2026-11-13 현재 Master 경로·브랜치·HEAD `272d576ac3ed89f18873940fbad2f759b3ae9d04`·빈 index·기존 dirty를 직접 확인했다. 위 소스·catalog 관찰은 최초 기획 작성 때의 근거이며 이번에 제품·DB 조사를 반복하지 않았다. 첨부 검수 명세와 지정 문구만 대조했다.
- **순서:** [현행 대기열](../project-memory/다음-작업-우선순위.md#resume-point)의 E(공지·고객센터) → C(튜토리얼) → D(반응형 글꼴 제한)를 따른다. E는 기존 텍스트·접근성 계약으로 검증한다. D를 E의 착수 조건으로 되돌리지 않고, D 변경 시 E/C의 영향 표면만 다시 확인한다.

## 4. 결정 이유와 동작 계약

### 4.1 화면·시안·복귀

사용자 시안 10장 중 고객센터 8장·공지 2장. 보완안의 전역 번호와 첨부 내 폴더 번호가 다르므로 아래 화면 ID로 관리한다. 날짜·건수·문구·구독 상태·거래는 시안 예시일 뿐 운영 데이터가 아니다. 공통 `AppText`·`AppTextInput`·CTA·기존 배경/글라스와 읽기 가능한 먹색·회색 보조·보라 강조를 사용한다. 일반 텍스트와 입력·조작은 실제 요소로 그린다. 헤드셋/메모, 확성기, 말풍선, 접수 봉투는 화면 PNG에서 확인했지만 편집 원본·독립 투명 자산은 확인되지 않았다. 추후 원본 확보 또는 동일 톤의 승인 자산으로 대체한다. 화면 전체를 이미지로 붙이지 않는다.

공통 상태: 최초 로딩은 구조 유지, 빈 상태와 오류 구분, 추가 페이지 실패는 기존 항목을 보존하고 그 위치에서 재시도. 오프라인에서 신규 쓰기 성공을 표시하지 않는다. 앱은 권한 상실·세션 변경·접근 불가·게시 중단을 감지한 뒤 원문을 즉시 가리고 관련 캐시를 무효화한다. 문의 등 민감 본문·초안·이미지는 계정·세션·권한 경계에 맞춰 정리한 뒤 안전한 상위 화면으로 복귀한다. 현재 세대·접근 상태와 맞지 않는 지연 응답은 폐기하고 재검증에서 비접근으로 판정한 본문을 캐시에서 다시 노출하지 않는다. 서버 확정 시점의 신규 접근 차단과 오프라인 사본의 한계는 §4.5를 따른다. 권한 유효한 단순 revision 충돌 및 동일 계정·세션의 단순 이동에서는 기존 초안·필터·스크롤 보존 계약을 유지한다. 조작 범위는 기존 접근성 계약을 지키고 48dp를 목표로 한다.

### 4.2 구독 화면 선제작·전체메뉴 미리보기

- 개발 전용 `구독자 미리보기` 버튼을 [등록 후 로딩 미리보기](../../src/screens/Auth/PostRegistrationLoadingReview.tsx)와 같은 경계로 둔다. [전체메뉴 상단](../../src/screens/More/MoreDrawerContent.tsx)의 현재 닉네임·펫 정보 컴포넌트를 재사용한다. **기본/구독자**를 화면 안에서 전환하고 종료/다시 진입 시 기본값으로 돌아간다. 일반 화면의 디자인이나 계정 값을 토글하지 않는다.
- 구독자 변형은 얇은 보랏빛 테두리와 닉네임 옆 작은 ‘구독’ 배지로 시작한다. 기본 정보·펫 정보·기존 버튼의 배치 유지가 우선이며 테두리가 정보 영역의 실측 크기·정렬을 의도치 않게 바꾸지 않도록 한다. 배지는 닉네임 옆 허용 공간에 두고 긴 이름은 기존 줄바꿈·말줄임 계약을 따른다. 다음 줄 배치는 펫·버튼 위치를 바꿀 수 있으므로, 예외가 필요하면 허용 높이 변화와 이동 가능한 요소를 좁은 폭 계약 및 PO 시각 확인 항목으로 명시한다. 미확정 예외를 기본 합격 조건으로 사용하지 않는다. 같은 논리 폭·fontScale·닉네임·펫 정보로 두 상태를 비교하며 S25 Edge·PO Metro 조정·E→C→D를 유지한다. 미리보기를 이유로 일반 화면·전역 폰트·전체메뉴 구조를 바꾸지 않는다.
- C01~C03은 미리보기 내부에서만 연결하고 가상 거래·접수임을 항상 식별한다. 화면 구성·입력·상태·오류 컴포넌트는 후속 운영 연결에서도 재사용하되, 미리보기에는 로컬 예시와 내부 동작만, 운영 연결에는 검증된 서버 데이터와 실제 명령을 연결한다. 미리보기 상태는 화면 로컬에 두며 실제 entitlement·계정·주문·문의/알림 배지·서버 캐시와 공유하거나 변경하지 않는다. 기존 닉네임·펫 정보는 읽기 전용 재사용이고 진입 때문에 새 프로필·거래 조회를 만들지 않는다.
- 미리보기 진입·전환·예시 접수·복귀가 유발하는 서버 읽기·쓰기·첨부 업로드·analytics·외부 스토어/결제/실제 문의 경로 이동은 모두 0이다. 기존 앱의 독립적인 background 요청과 구분한다. 닫기·Back은 원래 메뉴 위치, 종료·재진입은 기본값, 계정·세션 전환은 미리보기 폐기다. Release 진입 차단은 PV01-E의 실제 후보 검증 대상이며 버튼 숨김만으로 완료되지 않는다.

### 4.3 공지·FAQ의 공개 모델

**설계 권고:** 초기 게시판 공개본·작업본을 알림 `announcements`와 물리적으로 분리된 앱 공지 도메인에 둔다. 게시판 원장은 하나이고 기존 `announcements`는 기존 알림 용도다. 재사용 우선 검토에서 분리 권고로 바꾼 이유는 §2에서 확인한 가상 알림함과 fanout 모두 활성 all 행을 소비하고 target_scope 제약이 있어 좁은 읽기 projection만으로 게시판 무발송을 보장하지 못하기 때문이다. 소비 경로를 둘 다 바꾸는 안은 기존 수락 경계에 영향을 준다. 기존 행 자동 이관·자동 동기화·기존 알림 소비 경로 변경은 이번 범위가 아니다. 향후 필요한 게시판 글은 운영자의 명시 검토·게시를 거치고 의도적 알림은 별도 명령이다. 신규 게시판 최초 게시·수정·중단·재게시 자체로 기존 알림함 가상 공지·fanout 대상·delivery·OS 발송이 추가되지 않아야 하며 게시판 재조회·최소 무효화 신호는 허용한다. QA08은 대상 공지·작업 ID 상관관계 또는 격리 시험으로 판정하고 무관한 기존 알림 증가는 실패로 계산하지 않는다. 새 물리 테이블명·RPC명·migration은 이번에 확정하거나 만들지 않는다.

- 개념 저장 단위: 공지·FAQ의 공개/작업본, ticket, 공개 메시지(불변 순번), 읽음 cursor, 업로드 의도/불변 첨부, 요청 결과, 최소 감사, 전달 outbox. 물리명은 승인된 단계 0에서 확정한다. 관리자 역할·담당자 개인정보·내부 자료는 사용자 DTO에서 제외한다.
- 명령과 실패: 작업본 저장은 ID+revision, 게시/중단은 작업본 및 공개 revision+요청 key. 최초/추가 문의는 유형 또는 ticket, key, 텍스트 또는 ready 첨부 ID와 초안 ID. claim/시작/인계/종료는 ticket+revision, 인계/운영 종료 사유. 답변은 ticket+key+revision+마지막 본 사용자 순번+답변 종류. 읽음은 ticket+실제 표시 순번, 첨부 조회는 첨부 ID. 성공은 변경된 ID/버전/시각 또는 cursor를 반환한다. 권한·비접근/없음·revision·새 메시지·담당 충돌·첨부 미준비·한도·일시 실패는 안정된 오류 코드로 구분하고 한국어 안내에서 타인 문의 존재나 원문을 노출하지 않는다.
- 전송 중 / 전송 확인 중 / 확정 실패 / 완료를 구분한다. 현재 actor·세션·접근 권한 → 형식·크기·fingerprint → 기존 동일 요청 결과 → **신규 요청만** 현재 revision·첨부 미연결·rate limit 검사 → commit 순서. actor+operation+key와 동일 내용이면 최초 결과, 다른 내용은 충돌. 성공 응답 유실 시 같은 key로 먼저 복구한다. 명시 거부 후 수정 제출만 새 key, 같은 초안의 ready·미연결 사진은 재사용 가능. 접수·메시지·첨부 참조·요청 결과·감사·outbox는 한 DB transaction; 업로드와 발송은 밖. 관리자 권한 상실이 확인되면 초안을 보존하지 않는다.
- 최초·추가 문의 모두 공백 아닌 텍스트 또는 검증 사진 1장 이상. 사용자 2,000자, 운영자 5,000자, 사진 3장×변환 후 5MiB, JPEG/PNG/WebP는 권고. 전체 payload·픽셀·이미지 입력 용량/시간 상한, 요청 영수증 보존·재시도 기간을 별도로 확정한다. 신규 문의 10분당 3건, 메시지 분당 20건은 운영 검토값; 동일 요청 재시도는 중복 차감하지 않는다.

### 4.5 권한·첨부·알림·복구

서버에서 권한 회수가 확정된 뒤 시작된 신규 민감 조회·쓰기·첨부 조회는 기존 JWT로도 현재 권한 검사에서 거부한다. 공지 중단 확정 뒤 시작된 일반 사용자의 신규 목록·상세 조회에는 해당 공지를 반환하지 않으며, 권한 있는 관리자의 관리·감사 조회는 기존 계약을 따른다. 앱의 감지 후 정리는 §4.1대로 수행한다. 회수·중단 전에 시작된 요청도 결과가 현재 세대·접근 상태와 맞지 않으면 폐기한다. 재검증으로 접근 불가를 확인한 본문은 캐시에서 다시 표시하지 않는다. 오프라인 기기의 이미 받은 사본을 서버 회수 시각에 원격 제거한다고 보장하지 않는다. 최소 Realtime 신호 뒤 현재 권한으로 재조회하며 전역 JWT·Auth 정책은 변경하지 않는다.

| 주체/경로 | 권한 및 데이터 경계 |
| --- | --- |
| 비로그인·일반 사용자 | 비로그인은 확정된 공식 연락 안내만 제공하고 기존 공지 정책은 유지. 일반 사용자는 자기 ticket·공개 메시지·연결 첨부만 읽고 자기 접수·추가·읽음·명시적 해결만 실행. 타인 ID·집계·첨부·target은 직접 API에서도 차단. |
| 운영자 | 공지 작성/게시, FAQ 작성/게시, 문의 조회, 담당 답변/종료, 사유 있는 인계 권한을 최소 분리. UI와 독립적으로 매 읽기·쓰기에 서버의 현재 권한과 필요한 세션 유효성 검사. role·actor·owner를 요청값/사용자 metadata/로컬 캐시로 받지 않는다. |
| Data API·DB | 노출 table/view/RPC와 RLS·grant 각각 점검. 일반 사용자의 직접 상태·감사·outbox 쓰기 금지. invoker 우선, 필요한 definer만 비노출 내부 경계·고정 search_path·명시적 권한 검사·최소 EXECUTE. 새 JWT/전역 Auth 정책 없음. 감사 actor·행위·대상·시각·revision·결과만 남기고 민감 원문은 복제하지 않는다. |
| 비공개 첨부 | 계정+초안 ID로 업로드 의도 발급 → 전용 비공개 임시 업로드 → 서버 MIME/decode/픽셀·바이트·EXIF/GPS 검증 및 안전 재인코딩 → 불변 ready object → DB에서 1회 연결. 덮어쓰기 금지, 실패 사진을 자동 누락하지 않음, 미연결 정리와 연결 경쟁은 조건부 상태 전이/잠금으로 방지. 미연결 24시간은 후보, 접수 보관과 별도. |
| 첨부 읽기·회수 | ID로 현재 권한을 검사해 바이트 반환, `private, no-store`와 세션별 이미지·임시파일 정리 검증. 최종 object 직접 조회/서명 발급 우회 차단. 공개 URL, 장기 signed URL redirect, 임의 URL proxy 금지. 캐시와 이미 내려받은 사본의 즉시 원격 회수는 보장하지 않는다. |
| 배지·전달 | 내역은 읽지 않은 운영자 답변이 있는 **문의 수**, 큐는 staff 응답 필요 **문의 수**. 게시판 공지는 §4.3의 작업 귀속 무발송 계약을 따른다. 운영자 답변은 문의 작성자 한 명에게 내용 없는 논리 인앱 알림을 event/recipient/channel별 한 건 생성하고 앱 표시를 중복시키지 않는다. 재시도에 따른 여러 전송 시도와 외부 경로의 정확히 한 번 배달은 구분한다. 신규 접수는 운영 큐에 반드시 반영하되 관리자 알림·OS push 확대는 별도. outbox는 고유 키, claim/lease·발신 전 권한·대상 재검사, 제한 재시도와 최종 실패 관찰을 유지한다. 발송 실패로 접수/답변을 되돌리지 않는다. |
| 실시간·계정 | 서버 발신의 공개 변경/개인 최소 무효화 신호만, 본문·사진·결제·개인정보·메모 없음. 구독 확인 후 snapshot 또는 동등 handshake, ID/revision dedupe, focus/foreground/재접속 재조회. fallback은 활성 화면에서만 제한, 30초는 후보. 계정·세션 세대·권한·필터를 키에 포함하고 로그아웃·전환 시 요청·구독·timer·초안·이미지·pending target 정리. 늦은 결과는 세대 비교로 폐기, 서버 commit은 해당 계정에서만 복구. |
| 알림 이동·목록 | 기존 [변경 관찰](../../src/services/notifications/notificationSync.ts), [탭 처리](../../src/hooks/useOpenNotification.ts), [목적지 resolver](../../src/services/notifications/openNotification.ts)의 책임을 재사용한다. 인증 복원→현재 계정·대상 권한→현재 route→한 번 이동, 대상 화면 진입 성공 후 기존 알림 읽음과 대화 읽음은 각각의 계약으로 갱신. 명시 탭만 이동하고 단순 수신은 화면을 닫지 않는다. 타인/중단/삭제/만료는 안전한 안내. cold/warm·중복 탭·Back에 root reset/중복 mount 금지. 가상화 목록, ID key, 초기 대화 30건 후보, prepend/늦은 이미지 치수의 위치 고정, 과거 대화 읽을 때 새 메시지 이동 요소만 표시. |
| 보관·탈퇴·rollback | 본문·파일·감사·이벤트·로그·백업의 목적, 기산점, 기한, 파기·예외·접근·백업 지연을 각각 확정. 현재 탈퇴 finalizer와 소유자 검증 후 Storage 공식 삭제 경로 연결, FK 차단·고아 파일·재시도 확인. 공지 읽기/문의 쓰기/첨부/운영자 쓰기를 필요한 단위로 비활성화하고 기존 접수와 구버전 기능 보존; 파괴적 down migration 없음. |

초안 텍스트·첨부 URI·원문 응답을 범용 영구 저장소에 넣지 않는다. 같은 유효 계정·세션의 복귀에는 메모리 초안을 보존한다. 프로세스 종료 후 전송 확인이 필요한 경우에는 본문 대신 비민감 요청 식별자만 계정에 묶어 복구하고 서버에서 현재 권한을 다시 검사한다.

#### 4.5.1 실제 1:1 사진 첨부 구현안

**후속 구현과 한계:** [격리 실기기 실행](../project-memory/최근-작업-로그.md#nuri-15-ticket-photo-qa)에서는 로컬 검증기가 이미지를 재인코딩해 비공개 Storage에 저장하고, 메시지·첨부 연결은 단일 DB 트랜잭션으로 확정한다. 이 어댑터는 운영 배포물이 아니다. 운영 처리기·권한 회수 재검증·응답 유실 및 정리 경합·탈퇴 파일 정리는 아래 요구로 남는다.

현재 실제 문의 서버는 텍스트 전용이다. 예시 사진 상태는 실제 업로드 증거가 아니며, 이 절은 구현 계약이다. 운영 bucket·권한·데이터는 이번 차수에서 변경하지 않는다.

| 단계 | 앱 동작 | 서버 계약과 실패 처리 |
| --- | --- | --- |
| 선택 | 작성창의 사진 아이콘으로 기존 `services/media/photoPicker.ts`를 열고 썸네일별 삭제 버튼을 제공한다. 취소는 기존 입력에 영향 없다. 최초 문의와 기존 대화의 추가 메시지에 같은 동작을 적용한다. | 최대 3장, 변환 후 장당 5 MiB·합계 15 MiB 후보. JPEG/PNG/WebP만 최종 저장. HEIC은 지원되는 변환을 통과할 때만 받는다. |
| 임시 업로드 | 앱은 계정·세션 세대·초안 ID·첨부 ID에 진행 상태를 묶는다. 한 장 실패해도 텍스트와 다른 준비 사진은 유지한다. 사용자가 해당 사진을 제거하거나 다시 준비하기 전에는 자동 누락 전송하지 않는다. | 정상 세션 및 대상 문의 접근을 검사해 임의 서버 키의 **단일 임시 object**에만 업로드 의도를 발급한다. 클라이언트가 경로·소유자·MIME을 확정하지 않는다. 재시도는 서버 상태를 확인한 뒤 같은 준비 요청의 결과부터 복구한다. |
| 검증·연결 | 선택됨 → 업로드 중 → 검사 중 → 준비 완료 또는 실패. 텍스트 또는 준비 완료 사진이 있을 때만 보낼 수 있다. 첨부 확대와 선택기 복귀에서 키보드·초안을 보존한다. | 실제 바이트의 형식·decode·픽셀 수를 검사하고 EXIF/GPS를 제거해 불변 최종 object를 만든다. 메시지 제출 시 권한 확인과 기존 멱등 결과 조회를 먼저 하고, 새 요청만 초안/소유권과 준비 상태를 잠가 1회 연결한다. 메시지, 첨부 참조, 감사, 요청 결과는 한 DB transaction이다. |
| 열람 | 대화 메시지에서 준비된 첨부의 썸네일을 탭해 확대한다. 오류는 해당 사진에만 표시하고 재조회할 수 있다. 로그아웃·계정 교체·권한 상실 후 메모리/전용 임시 파일을 정리한다. | 불투명 첨부 ID로만 조회한다. 현재 세션과 문의 소유자 또는 현행 `support.manage` 권한 및 연결 관계를 확인한 뒤 바이트를 `private, no-store`로 전달한다. 최종 object에는 공개 URL, 직접 읽기·서명 발급, 장기 redirect를 열지 않는다. |
| 정리 | 닫기·취소로 화면이 사라져도 이미 접수된 자료는 지우지 않는다. | 미연결 객체에만 정리 기한을 적용하고 상태/락으로 연결과 충돌을 방지한다. 공식 Storage 삭제 API의 결과를 검증한다. 탈퇴·보관 종료는 승인된 별도 작업이며 DB 행만 삭제하고 종료하지 않는다. |

격리 우선 검사: 정상 사진 1장·사진만 보낸 최초 접수·기존 방 추가·3장 경계, 선택 취소, 일부 실패, 확장자 위장·픽셀 제한·EXIF, 업로드와 정리 경합, 동일 전송 재시도, 다른 계정과 회수된 운영자의 조회 차단, 접근 상실 뒤 앱 정리. 운영 전 보관기간·처리 책임을 확정한다. [Storage 권한](https://supabase.com/docs/guides/storage/security/access-control)과 [비공개 파일 응답](https://supabase.com/docs/guides/storage/serving/downloads)은 설계 근거이며 현행 동작 증거가 아니다.

## 6. 다음 액션

1. **별도 착수 승인 뒤 첫 작업 하나:** 공지 게시판 무발송·권한의 현황/계약 확정. 연결 환경을 고정하고 외부 caller·발행/읽음/삭제·구버전 영향과 공지 전용 권한의 경계를 먼저 대조한다. 완료 기준은 게시판 공개가 기존 inbox·delivery를 만들지 않는 설계와 격리 검증 조건 확정이다. 운영 게시, 부여, 변경은 이 단계에 포함하지 않는다.
