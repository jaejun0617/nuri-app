# docs/sql 정리 가이드

## 2026-11-09 역할과 실제 소비 관계

파일 존재·운영 적용 이력·현재 운영 정의는 별개다. 이번 정리는 로컬 소스와 기존 보존 기록만 대조했으며 운영 DB에 접속하거나 SQL을 실행하지 않았다.

| 역할 | 조사 시점 파일 집합 | 보호 기준 |
| --- | --- | --- |
| 버전 migration | supabase/migrations 133개 | 파일 수는 운영 적용 수가 아니다. 버전·내용·경로 보존 |
| 계약 검사·fixture | supabase/tests 40개 및 개별 smoke | 운영 migration과 별도 역할 |
| 재구축 입력 | docs/sql 55개 중 아래 10개 | 실제 배열 순서·경로 보존 |
| seed·수동 보조·진단 | docs/sql 및 scripts/verify_task2.sql | 파일명 분류는 잠정. 사용 조건·본문·승인 확인 |
| 참고본·mirror·과거 단계 | 날짜 지정 문서 SQL | 현재 운영 정의나 미사용을 단정하지 않음 |
| dump·백업 | 백업 SQL 2개 | public 범위 및 roles 실패 기록 보존. 전체 DB 복원 보장 아님 |

### 검사·CI 소비자

- Jest의 communityImageLimitContract는 docs/sql 커뮤니티 최종본과 migration을 직접 읽는다. communityDiscussionRead·guideSpeciesPlatform·timelineXpProgress도 migration 경로의 본문을 검사한다.
- scripts/qa의 notification-v3-sql-contract는 명시된 13개, notification-device-session-contract는 2개, title-v2-sql-contract는 3개 migration을 코드의 순서로 읽는다. 전체 migration을 자동 적용하는 검사가 아니다.
- walk-progression-duration-contract는 3개 명시 입력 뒤 migrations에서 `^\d+_walk_progression_active_duration\.sql$`에 맞는 파일을 찾아 정확히 1개인지 확인한다. 현재 매칭은 20261105081432 파일이다. 같은 basename의 tests 파일은 이 입력이 아니다.
- release-source-validation CI → package script → Jest → SQL 본문으로 간접 의존한다. 이 CI를 DB 배포 작업으로 해석하지 않는다.
- walk-phase4·phase5b QA는 출력 경로에 SQL을 동적 생성해 linked query에 전달하는 별도 도구다. 이번에는 실행하지 않았다.
- 사전 조사 inventory의 reference_graph는 주석·제외·basename 충돌을 포함하는 후보이고 verified_sql_dependencies는 확인한 읽기/실행 경계다. 외부 수동 소비자는 전수 확인하지 않았다.

최종·레거시·mirror라는 이름, 참조 검색 0건만으로 미사용·삭제 가능을 확정하지 않는다. SQL 이어 붙이기는 재구축 동등성 증명이 아니다. 병합·이동·개명·삭제·재적용·squash·repair에는 별도 승인과 소비 관계·운영 이력·복원 검증이 필요하다.

`docs/sql`은 사람이 읽는 최종 SQL 문서 세트를 모아 두는 기준 폴더다.

실행 이력은 `supabase/migrations/`에 보존하고, `docs/sql`은 도메인별 최종본, 보조 SQL, legacy 문서를 읽기 쉬운 한글 구조로 유지한다.

## 분류 규칙

- `supabase/migrations/*`
  - 버전이 있는 실행 이력 파일이다. 파일 존재와 실제 운영 적용 여부는 구분한다.
  - 이미 적용된 migration 파일은 삭제/개명/이동하지 않는다.
- `docs/sql/<도메인명>/*-최종.sql`
  - 해당 도메인의 문서용 최종 source of truth다.
  - linked remote drift가 있으면 이 파일을 기준으로 차이를 분석한다.
- `docs/sql/<도메인명>/레거시/*`
  - 과거 단계 적용본, 문서 migration, 초안처럼 현재 신규 적용 기준으로 쓰지 않는 파일이다.
- `docs/sql/<도메인명>/*-보조.sql`, `*-추가.sql`, `*-정책.sql`, `*-seed.sql`
  - 최종본을 보완하는 기능 추가, 호환성, storage, seed, 점검용 SQL이다.
- `docs/sql/공용/*`
  - 신규 프로젝트 bootstrap이나 공용 기능 묶음용 SQL이다.
  - 현재 운영 remote의 exact mirror처럼 읽지 않는다.

## 운용 원칙

- 먼저 linked remote와 `supabase/migrations/*`를 보고 실행 상태를 확인한다.
- 그다음 `docs/sql/<도메인명>/*-최종.sql`로 사람이 읽는 최종 상태를 본다.
- 단계별 SQL은 소비 경로·적용 이력·고유 내용·복원 근거를 먼저 대조한다. 별도 승인 없이 통합하거나 `레거시/`로 이동하지 않는다.
- remote와 local이 다르면 최종본이라고 적더라도 운영 반영 완료로 쓰지 않는다.
- 현재 앱이 의존하는 RLS, trigger, function, RPC, Storage 정책은 근거 없이 제거하지 않는다.

## migration baseline 재구성 판단

- 현재 시점에는 `supabase/migrations/*`를 archive/delete 대상으로 올리지 않는다.
- 아래 사유는 이 가이드의 과거 baseline 판단 이력이며 2026-11-09 운영 재조회 결과가 아니다. 당시 `supabase/migrations/*`가 최근 커뮤니티 delta 위주 실행 이력이라 프로젝트 전체 baseline 세트가 아니고, linked remote full schema dump를 확보하지 못했으며, `반려동물과-여행` local-only 최종본과 프로필 닉네임 정책 remote-only drift가 남아 있기 때문이다.
- 새 빈 DB를 baseline만으로 재구축 가능하다고 판단하려면 아래 조건이 먼저 충족돼야 한다.
  - linked remote full schema dump 또는 동등한 catalog 캡처 확보
  - local-only / remote-only drift 해소
  - 빈 DB 기준 재구축 검증
  - 현재 앱 runtime 계약과 baseline SQL의 정합성 재검증
