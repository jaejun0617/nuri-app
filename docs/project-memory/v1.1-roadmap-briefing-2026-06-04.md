## 2. V1.1 전체 작업 리스트

### 1. 산책/location discovery 자체 POI DB + Supabase PostGIS

- 목적: Kakao Local controlled-server-call 구조를 자체 POI 기반으로 전환하고 사용자 runtime provider 의존을 제거한다.
- 왜 V1.1인지: 신규 table, PostGIS index, RLS, RPC, seed/import 운영 설계가 필요해 V1.0 Code Freeze 범위가 아니다.
- 예상 영향 범위: 산책 리스트/상세, location discovery query, Supabase schema/RPC, admin import pipeline.
- DB/migration 필요 여부: 필요. POI canonical table, source/import/audit table, review queue, PostGIS/trigram/full-text index, public projection RPC가 필요하다.
- 앱 코드 영향: 기존 산책 list/detail UX는 유지하되 provider seed 호출을 자체 POI RPC read path로 교체한다.
- 운영/정책 영향: Candidate/Trust/User Layer 분리, public projection 정책, seed provenance, source attribution, 운영자 승인 기준이 필요하다.
- 위험도: High.
- 선행 조건: schema/RLS/RPC 설계 PR, seed source 선정, migration rollback 계획, Android smoke 계획.
- 추천 우선순위: 1순위.
- 이번에 바로 착수 가능 여부: 가능. 단 첫 단위는 설계 PR이며 실제 table 생성은 다음 구현 턴에서 별도 승인 후 진행한다.

### 2. Kakao Local runtime 제거

- 목적: V1.0 controlled-server-call 상태를 provider-zero에 가깝게 전환한다.
- 왜 V1.1인지: 자체 POI coverage와 fallback UX가 먼저 있어야 사용자 화면 품질이 깨지지 않는다.
- 예상 영향 범위: `location-discovery-seed`, Edge Function 캐시/TTL, 앱 empty/fallback UI.
- DB/migration 필요 여부: 자체 POI 전환과 함께 필요하다.
- 앱 코드 영향: 사용자 runtime에서 Kakao Local seed 요청을 제거하고 자체 POI 결과 없음 상태를 명확히 처리한다.
- 운영/정책 영향: Kakao Local은 admin seed 보조 도구로만 제한하고 provider key는 사용자 runtime과 분리한다.
- 위험도: Medium-High.
- 선행 조건: 자체 POI read path와 seed coverage 최소 기준.
- 추천 우선순위: 2순위.
- 이번에 바로 착수 가능 여부: 자체 POI 설계와 묶어 착수 가능하다.

### 3. MapLibre / PMTiles / 자체 지도 스택 후보 검토

- 목적: Google/Kakao 지도 API 비용 의존을 줄이고 OSM 기반 지도 후보를 검토한다.
- 왜 V1.1인지: 지도 엔진 교체는 Android 회귀 범위가 크고 V1.0 외부 지도 앱 deep link 전략을 흔들 수 있다.
- 예상 영향 범위: 지도 preview, location detail, tile hosting, offline/cache 전략.
- DB/migration 필요 여부: 직접 DB migration은 선택 사항이나 PMTiles metadata/hosting 운영 설계가 필요하다.
- 앱 코드 영향: MapLibre React Native 도입 시 native dependency와 Android build 영향이 크다.
- 운영/정책 영향: 타일 license, attribution, CDN/R2/Supabase Storage 비용, 한국/수도권 coverage 검증이 필요하다.
- 위험도: High.
- 선행 조건: 자체 POI milestone 이후 지도 preview 요구사항 확정.
- 추천 우선순위: 8순위.
- 이번에 바로 착수 가능 여부: 조사/스파이크만 가능. 구현 착수는 보류한다.

### 4. Naver OAuth cleanup

- 목적: V1.0에서 soft disable한 Naver OAuth를 출시 후 정리한다.
- 왜 V1.1인지: V1.0에서는 Google/Kakao로 provider scope가 닫혔고, Naver hard delete는 안정된 auth surface를 흔들 수 있다.
- 예상 영향 범위: `signInWithNaver`, provider config, `.env.example`, docs, Supabase `custom:naver` 운영 판단.
- DB/migration 필요 여부: 없음.
- 앱 코드 영향: hard delete 여부에 따라 auth service와 UI guard 정리가 필요하다.
- 운영/정책 영향: Supabase provider 유지/삭제, Naver Developers 설정 보존 여부 결정이 필요하다.
- 위험도: Low-Medium.
- 선행 조건: 출시 후 실제 운영 로그와 PO의 Naver 재도입 의사 결정.
- 추천 우선순위: 10순위.
- 이번에 바로 착수 가능 여부: 문서 cleanup 계획만 가능. hard delete는 보류한다.

### 5. Apple 로그인

- 목적: iOS 출시 또는 Apple 정책 대응 시점에 Sign in with Apple 범위를 판단한다.
- 왜 V1.1인지: V1.0은 Android-first이고 Apple login은 iOS 출시 정책과 연결된다.
- 예상 영향 범위: Supabase Apple Provider, Apple Developer 설정, iOS deep link, auth callback.
- DB/migration 필요 여부: 보통 없음. social consent snapshot을 열면 별도 설계가 필요하다.
- 앱 코드 영향: iOS 조건부 버튼, provider flow, callback/session 처리.
- 운영/정책 영향: Apple 심사 기준과 다른 social login 제공 여부 검토가 필요하다.
- 위험도: Medium.
- 선행 조건: iOS 출시 계획과 Apple Developer 계정 준비.
- 추천 우선순위: 12순위.
- 이번에 바로 착수 가능 여부: 아니오. Android-first V1.1 초기 마일스톤에는 제외한다.

### 6. 결제/구독 foundation

- 목적: 유료 기능을 entitlement 기반으로 열 수 있는 서버 계약을 만든다.
- 왜 V1.1인지: 결제는 DB/RLS/서버 검증/스토어 정책이 필요한 신규 상품화 트랙이다.
- 예상 영향 범위: `user_subscriptions`, `user_entitlements`, billing event contract, receipt validation, Google Play Billing.
- DB/migration 필요 여부: 필요.
- 앱 코드 영향: entitlement gate, paywall, subscription state UI, restore flow.
- 운영/정책 영향: 환불, grace period, billing event audit, server-side entitlement check가 필요하다.
- 위험도: High.
- 선행 조건: 유료 기능 범위와 가격/스토어 정책 결정.
- 추천 우선순위: 6순위.
- 이번에 바로 착수 가능 여부: foundation 설계는 가능하지만 자체 POI 이후가 적절하다.

### 7. Premium AI reply

- 예상 영향 범위: 편지함/추모 맥락, AI provider integration, generation log, entitlement gate.
- DB/migration 필요 여부: 필요. consent, generation log, cost tracking table이 필요하다.
- 앱 코드 영향: AI notice, consent UI, generation state, failure/cancel UX.
- 운영/정책 영향: provider policy, private content handling, abuse prevention, cost control이 필요하다.
- 위험도: High.
- 선행 조건: 결제/entitlement foundation, AI 정책 문구, 비용 cap.
- 추천 우선순위: 7순위.
- 이번에 바로 착수 가능 여부: 아니오. 결제/동의 foundation 이후가 맞다.

### 8. Guestbook private letters 확장

- 왜 V1.1인지: V1.0은 단순 private letter baseline이고 확장에는 visibility/abuse/AI 연계 정책이 필요하다.

- 앱 코드 영향: detail screen, edit/delete flow, list refresh/cache.
- 운영/정책 영향: private visibility, abuse/report 여부, timeline 연계 여부 결정이 필요하다.
- 위험도: Medium.

- 추천 우선순위: 5순위.

- 앱 코드 영향: public app 영향은 낮고 admin UI/API 영향이 크다.
- 운영/정책 영향: provider terms, source attribution, rollback, approve workflow가 필요하다.
- 위험도: Medium-High.
- 선행 조건: 자체 POI schema, admin role policy, provider key 격리.
