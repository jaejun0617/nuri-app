# 핵심 결정사항

## 문서 운영 원칙

- 더 이상 과거 Task 번호 체계를 source of truth로 쓰지 않는다.
- 현재 메모리는 `기능 이름`, `운영 계약`, `현재 구현 lane`, `후행 출시 게이트` 기준으로 관리한다.
- 구현 완료와 운영 완료를 같은 말로 쓰지 않는다.
- 출시 판단은 항상 `코드 + linked remote + 실기기/row-level 증적 + release checklist` 조합으로 한다.
- 다만 현재 최상위 목표가 구현 완료일 때는 release checklist를 `마지막 게이트`로만 해석한다.

## 현재 우선순위 모드

- 현재 NURI의 최상위 목표는 `즉시 배포`가 아니라 `핵심 task 구현 완료`다.
- 따라서 `task18 release readiness`는 유지하되, 지금 당장 모든 lane을 그쪽으로 맞추지 않는다.
- 구현 lane과 release lane을 절대 같은 우선순위로 섞지 않는다.
- 현재 구현 lane의 시작점은 `우리동네 동물병원`, `Guestbook -> private letters`, typography rollout, social auth 계약, entitlement foundation, Premium AI 선행조건이다.

## 정책 문서와 가입 흐름

- 정책 문서 source of truth는 `src/services/legal/documents.ts`다.
- 회원가입과 More는 실제 public 문서를 연다.
- 정책 문서는 앱 화면만 정리해도 완료가 아니며, public URL과 앱 복귀 검증이 있어야 닫는다.

## 비밀번호 재설정

- 비밀번호 재설정은 `request -> recovery link -> 앱 복귀 -> 새 비밀번호 설정 -> SignIn 재진입` 계약으로 고정한다.
- recovery 세션은 일반 로그인 세션과 분리해 다룬다.
- reset 완료 후 기존 계정 컨텍스트로 새면 blocker로 본다.

## 계정 탈퇴 7일 유예

- 계정 탈퇴는 `요청 즉시 로그아웃 + 7일 유예 + 복구 가능 + 유예 종료 후 자동 파기` 구조로 고정한다.
- Day 0에는 서버 원본을 보존하고 로컬 세션만 정리한다.
- 유예기간 로그인은 허용하되 앱 내부 진입은 막고 복구 모달만 연다.
- 최종 삭제는 `Scheduled Edge Function + DB finalizer + storage cleanup queue` 구조로 운영한다.
- 자동 파기 worker는 request 단위 fault isolation을 유지하며, object not found는 cleanup 성공으로 수렴한다.

## 커뮤니티 운영 방어선

- 커뮤니티는 moderation 없는 기능 확장을 금지한다.
- write-path는 rate limit, dedupe, blocked-term, stable error contract를 공통으로 사용한다.
- 신고는 self-report 차단, duplicate 차단, reporter flag trace, unique reporter 기준 auto-hide, moderation queue/action log를 기본 계약으로 둔다.
- hidden/auto_hidden/deleted/banned 상태에서는 이미지 비노출과 cleanup pending 추적을 우선한다.

## 공개 신뢰도

- 공개 라벨은 `후보`, `확인 필요`, `검수 반영` 3개만 사용한다.
- `confirmed`는 계속 닫아 둔다.
- personal state는 public trust를 직접 올리지 않는다.
- stale, source conflict, onsite check 필요 상태에서는 더 보수적인 공개 라벨을 우선한다.

## 우리동네 동물병원 Trust Gate

- animalHospital public projection은 `phone`, `coordinates`, `thumbnail`에 대해 open-by-default 정책을 사용한다. official canonical 값, `pending` verification, provider fallback이 있으면 public에 반영한다.
- `open24Hours`, `exoticAnimalCare`는 계속 approved verification 기반 filter gate로만 사용한다.
- provider enrichment 결과는 `phone`, `coordinates`, `thumbnail`의 경우 public fallback 소스로도 사용하지만, `held/rejected`는 계속 검수 자료로만 남긴다.
- `24시 운영` 칩은 병원명 문자열 신호를 사용하지 않고 approved `open24Hours=true`만 사용한다.
- public badge도 같은 원칙을 따른다. `[24시간 진료]`는 approved `open24Hours=true`만 사용하고, Google opening hours는 `[영업 중]`/`[영업 종료]` provider badge에만 쓰며 6시간 TTL이 지나면 숨긴다.
- provider photo는 강한 match면 `pending` public fallback으로 적재하고, 약한 match는 `held`로 남긴다.
- 리스트는 주소를 노출하지 않고 썸네일, `동물병원` label, 병원명, 전화번호만 우선 노출한다.
- user report flow와 public trust는 분리한다. 동물병원 신고 CTA는 별도 schema, moderation, abuse 방어선 결정 전까지 열지 않는다.

## 공용 place enrichment 엔진

- 동물병원과 산책 도메인의 provider enrichment는 공용 engine으로 처리한다. 도메인별 ad-hoc API 호출이나 client-side Google 호출은 금지한다.
- 앱은 화면 렌더링 직후 Supabase Edge Function `place-enrichment-demand`를 비동기로 호출하고, provider 호출/예산/캐시/중복제거는 모두 서버에서 처리한다.
- provider cache의 source of truth는 `public.nuri_place_provider_cache`이며, `cache_expires_at` 기준 30일 TTL이 지나면 stale로 간주한다.
- Google Places 신규 호출은 `claim_nuri_place_enrichment_budget` RPC의 월 하드캡 안에서만 허용한다. 예산 초과 시 demand 경로는 cache-only로 강등한다.
- 동일 place key에 대한 동시 demand는 `nuri_place_enrichment_jobs` claim/complete 계약으로 병합한다. 여러 사용자가 동시에 같은 장소를 요청해도 provider 호출은 1회만 허용한다.
- background cron도 같은 shared adapter와 같은 budget RPC를 사용한다. `place-enrichment-worker`는 10분마다 제한된 `limit/maxUnits` 안에서만 동작한다.
- `phone`, `coordinates`, `thumbnail`만 pending public fallback 대상이다. `open24Hours`, `exoticAnimalCare`는 enrichment와 무관하게 approved-only를 유지한다.
- Task 10 detail enrichment에서만 `hours`, `website` requested field를 사용한다. `currentOpeningHours` 기반 영업 상태는 `dynamic_status_expires_at` 6시간 TTL 안에서만 public badge로 소비한다.
- Task 9 산책 seed는 `location-discovery-seed` Edge Function에서 Kakao Local을 호출한다. 앱 클라이언트는 Kakao REST API를 직접 호출하지 않는다.
- provider photo를 public에 쓸 때는 attribution 문자열을 함께 저장하고 카드/상세에 노출한다.
- V1.0 운영 기준에서는 Google provider cache 30일 TTL 아키텍처를 프로젝트 표준으로 고정한다. 법무/약관 리스크는 제품 판단으로 관리하고, 엔지니어링은 TTL/예산/attribution/중복방지 구현을 우선한다.

## 날씨 provider cache

- 날씨 클라이언트는 Open-Meteo forecast/air-quality endpoint를 직접 호출하지 않는다.
- 앱은 Supabase Edge Function `weather-cache`만 호출하고, provider 호출/API key/customer endpoint 선택은 서버에서만 처리한다.
- weather cache source of truth는 `public.nuri_weather_cache`이며 앱 클라이언트 직접 select/insert/update policy는 열지 않는다.
- cache key는 raw latitude/longitude가 아니라 0.02도 좌표 bucket과 `locale|timezone` 조합이다. 원본 정밀 좌표와 user id를 함께 저장하지 않는다.
- forecast와 air quality는 한 bundle로 묶어 fresh 60분 TTL을 적용한다.
- provider 실패 시 `stale_until` 6시간 안의 stale bundle을 `stale_cache`로 반환하고, stale cache가 없으면 stable error code를 반환한다.
- Open-Meteo Free/Open endpoint는 production commercial path로 고정하지 않는다. customer API 사용 시 `OPEN_METEO_*` 환경변수와 Supabase secret만 사용한다.
- Open-Meteo attribution은 날씨 카드/상세에서 작게 표시한다.
- 2026-04-30 기준 `nuri_weather_cache` remote apply, `weather-cache --no-verify-jwt` deploy, 수동 smoke, Android `SM_S937N` 홈/상세 QA, logcat direct Open-Meteo 0건 검증까지 완료되어 v1.0 날씨 도메인은 close한다.
- Open-Meteo customer API key/계약 전환과 public no-JWT endpoint abuse throttle은 v1.1 운영 부채로 관리한다.

## Private Letters

- Guestbook의 공개형 확장은 금지하고, 탭의 제품 의미는 펫별 private letters로 전환한다.
- 기존 `GuestbookTab` route 이름은 앱 복귀 흐름을 위해 유지하되, 사용자 표시명은 `편지함`으로 쓴다.
- `letters` table은 현재 단계에서 user-authored private letter만 다룬다.
- AI 답장, 공유, 신고, 공개 댓글은 consent, entitlement, generation log, moderation 정책 전까지 열지 않는다.

## Android UI 기준

- Android 실기기 기준으로 읽기 쉬운 타이포와 안정적인 탭/헤더/모달 구조를 우선한다.

- 긴 폼의 키보드 대응은 단일 스크롤 계약으로 유지한다.
