# advanced-codex-workflow.md

승인 범위 안에서 원인 분석 → 최소 수정 → 검증 → 전달을 수행하는 실행 절차를 소유한다. 2026-11-11 PO 운영지침 개편 기준이다. 현재 수락·대기열은 이 문서에 복제하지 않는다.

진입: [AGENTS](../../AGENTS.md) · [검사 적용성](advanced-codex-checklist.md#applicability) · [사실별 근거와 기록](advanced-codex-memory.md#authority-map) · [현재 상태](../project-memory/현재-프로젝트-상태.md#current-baseline) · [재개 지점](../project-memory/다음-작업-우선순위.md#resume-point).

<a id="execution-contract"></a>
## 실행 핵심과 작업 계약

1. 실제 경로·branch·HEAD·index·dirty·untracked와 현재 PO 지시를 확인한다. 과거 worktree나 ZIP으로 현재본을 덮어쓰지 않는다. 적용 AGENTS와 이 절, 현재 상태·우선순위·직전 관련 로그를 읽고 태스크에 필요한 계약·원장 행·소스·증거로 확장한다.
2. 목적, 허용 환경, 변경 가능 영역, 금지 조치, 성공 조건, 전달 범위, 후속 전환 조건을 짧게 기록한다. 시스템·보안·도구 권한이 경계이며, 과거 지시·기획서·위험 보고가 새 권한을 만들지 않는다.
3. Master가 단독으로 논리 작업 단위를 순차 처리한다. 승인된 A→B→C 묶음은 한 계약으로 관리한다. [8/05 Room 절차](../handoffs/2026-08-05/NURI-MASTER-TASK-ROUTING-POLICY.md#historical-scope)는 당시 기록이지 현재 위임 의무가 아니다.
4. 이미 승인된 조사·로컬 수정·검사·QA 준비·필요 빌드·설치·전달은 계약 안에서 이어간다. 파일 수는 영향 신호이지 재승인 기준이 아니다.
5. 신규 제품 정책, 파괴적 사용자 데이터 변경, 운영 권한·수신자 확대, 비용·외부 발송·배포·출시는 실제 승인 범위를 확인한다. 기존 승인으로 충족되지 않으면 해당 단계의 구체적인 최소 결정을 요청한다.
6. 위험은 권한·데이터·외부 계약·회귀 범위·복구 가능성으로 판단한다. MD 7파일이 승인 안일 수 있고 RLS 1파일이 별도 승인을 요구할 수 있다. 작은 diff를 저위험으로 단정하지 않는다.

읽기 전용/Final Review는 승인된 읽기·분석·보고만 한다. 저장소 메모리·코드·SQL·기기·데이터를 자동 갱신하지 않는다. 사용자가 허용한 외부 보고서 저장과 저장소 쓰기는 구분한다. 문서 수정 승인도 제품 기능 실행 승인이 아니다.

<a id="diagnosis"></a>
## 원인 분석과 실패 대응

- 현상·실패 단계·관찰 증거 → 원인 가설 → 가설을 구분하는 최소 확인 → 결과 → 최소 수정 또는 다음 안전한 확인 순서다. 정적 위험과 실제 재현 결함은 구분한다.
- 동일 입력·동일 가설·동일 관찰 수단에 새 근거가 없으면 실패를 반복하지 않는다. 승인 안의 다른 안전한 수단으로 전환한다. 일시 오류는 멱등성과 실제 오류에 맞는 유한 재시도만 한다.
- 서버 저장 뒤 응답이 유실되면 같은 논리 요청 ID의 결과부터 확인한다. 새 원본을 중복 생성해 성공 표본을 골라내지 않는다.
- 타입·빌드·테스트 실패나 회귀에서는 배포·수락 승격을 중단한다. 로그·현재 변경을 보존하고 실패가 Git·서버·데이터에 이미 반영됐는지 확인한다. 독립적인 승인 조사와 최소 복구는 계속할 수 있다.
- 사용자 기존 변경과 자신의 변경을 분리한다. 확인된 원인에 필요한 자기 변경만 보정하고 동일 조건을 재검증한다. 전체 작업 롤백, 무단 reset/restore/stash/clean, 테스트 기대값 약화, 권한 완화, 타입 무시로 통과시키지 않는다.
- DB 복구는 앱 코드 복구와 다른 권한·순서·데이터 위험을 가진다. 원상복구가 확실하지 않으면 현 상태·정확한 ID·부작용과 필요한 판단을 남긴다. 전역 rollback을 추정 실행하지 않는다.
- 관찰 도구가 놓친 것과 제품 실패를 구분한다. 관측되지 않은 결과는 PASS가 아니며, 현재 환경에서 닫을 수 없는 정확한 조건만 BLOCKED/PARTIAL로 남긴다.

<a id="continue-stop"></a>
## 계속과 중단

- 선행 조건을 충족한 승인된 후속 단위는 중간보고 뒤 계속한다. 단건마다 같은 승인을 다시 묻지 않는다.
- 직접 OAuth 인증·외부 자원·범위 밖 권한이 필요하면 그 행에 필요한 최소 입력을 구체적으로 요청하고 독립적인 승인 작업은 이어간다. 비밀번호·MFA·토큰을 요청하거나 보안 절차를 우회하지 않는다.
- 명시 STOP, 단건 종료, 승인 범위 종료, 예상 밖 사용자 데이터 위험, 실행 환경 단절에서는 안전한 체크포인트를 남기고 멈춘다. 실행하지 않는 백그라운드 작업이나 완료 시각을 약속하지 않는다.
- 완료는 해당 계약의 필수 조건 충족이다. 미실행·보류를 분모에서 빼거나 PASS로 바꾸지 않는다. 이번 실행 범위 완료, 원래 통합 동결, 출시 승인은 별도다.
- 후속 범위가 미승인이면 정확한 다음 한 지점만 인계한다. 이 규칙이 현재 PO의 '문서 개편 후 U2 자동 재개 금지'를 해제하지 않는다.

<a id="verification"></a>
## 검사 선택

검사표는 [Checklist 작업 유형별 적용성](advanced-codex-checklist.md#applicability)이 소유한다. 이번 변경의 영역·위험과 기존 증거 재사용을 근거로 항목을 고르고 결과·미실행 이유를 남긴다. MD-only에는 원문·링크·diff·필수 CI를 적용하고 APK·설치·수동 제품 전체 재검사는 하지 않는다. 서버만 바뀌었으면 앱 입력 불변 상태에서 자동 APK 재빌드를 하지 않는다.

## Metro 개발과 설치본 최종 수락

2026-11-11 PO의 [개발·수락 분리 결정](../project-memory/핵심-결정사항.md#2026-11-11-metro-개발과-설치본-수락-분리)을 적용한다.

- JS/TS·스타일·일반 UI는 타입·대상 lint·표적 테스트와 Metro/Fast Refresh를 우선한다. 작은 수정마다 전체 Gradle build·설치를 반복하지 않는다.
- Native/Kotlin·Manifest·Gradle·네이티브 의존성 또는 번들 입력이 바뀌면 필요한 빌드를 한다. Fast Refresh로 Native 변경을 검증했다고 하지 않는다.
- 안정화된 한정 묶음의 소스와 runtime 입력을 고정하고 필요한 QA APK를 생성한다. 최종 기능 수락은 Metro OFF 독립 번들 설치본과 조건별 실제 서버·기기 증거로 판정한다. OAuth·알림·cold/warm·Android Back·전환·플리커는 필요한 실제 설치 경계를 확인한다.
- 제품 source SHA, 미커밋 runtime 차이, 환경 설정 hash, APK hash, 설치 기기·시각, Metro 상태, 증거 ID를 연결한다. QA 어댑터·backend·앱 ID가 다르면 별도 후보로 표시한다. Debug/Metro는 Release 성능 증거가 아니다.
- Fast Refresh의 effect 재실행만으로 제품 경합 결함을 확정하지 않는다. 해당 설치본 또는 독립 근거로 재현 여부를 확인한다.
- 변경 없는 기존 APK는 적합성을 확인해 재사용한다. 재개·모델 변경·문서 편집 때문에 빌드나 기존 PASS 전체를 반복하지 않는다. 필수 CI와 원장 조건은 생략하지 않는다.

<a id="code-domain-safety"></a>
## 코드와 도메인 보호

- 기존 패턴·theme token·AppText·공통 컴포넌트·stable error code를 우선한다. [고정 디자인과 예외](../project-memory/핵심-결정사항.md#2026-11-06-po-고정-모든-후속-디자인의-cta와-글자-크기), 사용자 폰트·접근성·의미색을 보존한다. 시안이나 새 제안은 정책 변경 승인이 아니다.
- TypeScript strict, unknown 입력의 guard, nullable/optional, route params·DTO·domain model의 경계를 지킨다. any·ts-ignore·무책임한 fallback을 쓰지 않는다. 주석은 목적·비자명한 경계를 짧게 설명한다.
- 전역·서버·화면·파생 상태를 구분한다. 계정/선택 펫·query cache·draft·upload·subscription의 소유와 수명을 보존하고 늦은 응답·중복 요청·응답 역전·unmount를 처리한다.
- loading/error/empty/success 및 느린 네트워크·키보드·복귀·safe area·접근성을 영향 화면에서 확인한다. optimistic update 실패 복구와 목록/상세 정합성을 검증한다.
- 리스트 고유 key·dedup·loading guard·썸네일/원본·signed URL 비용을 구분한다. inline callback 존재만으로 결함이나 memo 필수라고 판단하지 않는다. 측정과 의존관계로 최적화 필요성을 확인한다.
- 설치된 React/RN·리스트 라이브러리의 실제 버전과 New Architecture 계약을 따른다. React 19 ref 또는 EAS channel/branch는 실제 사용 시에만 확인하며 신규 도입·전면 전환을 자동 수행하지 않는다.
- 커뮤니티는 moderation·abuse 방어·draft 보존·운영 감사·reporter trace를 먼저 지킨다. 서버 계약 없는 조회수, client-only 비속어 차단, create만 막고 update/comment 우회를 남기는 확장은 금지한다.
- 장소·여행은 Candidate / Trust / User Layer, freshness/stale/conflict, exposure budget·상단 점유를 구분한다. 추천과 단순 표시를 혼동하지 않는다. 개인화로 public trust를 올리거나 미승인 confirmed를 열지 않는다.
- 정책 없는 가입 확장·권한 없는 운영 기능을 만들지 않는다. 가이드 CMS 운영 정책은 해당 가이드 도메인에 한정하며 신규 공지·고객센터 기획의 승인으로 전용하지 않는다.

<a id="qa-server-safety"></a>
## QA와 서버 경계

- 환경 → 정상 인증 경로 → 실제 앱 진입 → 서버/앱 사용자 동일성 → 필요한 합성 원본 → 앱 소비·읽음·Back → 정리 순으로 준비한다. 토큰 발급만으로 앱 진입 준비를 끝냈다고 하지 않는다.
- 계정 생성·fixture·서버 실행은 현재 승인된 정확한 소유자·원본·수신자·환경에만 한정한다. 과거 QA 생성 금지나 한정 생성 승인을 영구 정책으로 확대하지 않는다.
- fixture 사전 상태와 실제 업무 동작·결과를 분리한다. 알림 결과·read_at·보상 지급을 직접 써넣어 E2E PASS를 만들지 않는다. 앱 소비 전에 수신자·원본을 성급히 삭제하지 않는다.
- 격리 backend·앱 ID·서명·저장공간·유효 Auth·합성 데이터·외부 발송 차단을 확인한다. 운영 개인정보 복제·관리 키 앱 탑재·임의 JWT/uid·RLS 우회는 금지한다.
- SQL 실행 이력은 supabase/migrations, 계약 검사는 supabase/tests, 재구축·참고 입력은 docs/sql과 scripts의 **실제 소비 경로**를 따른다. [SQL 가이드](../sql/정리-가이드.md)를 확인한다. docs/sql 전용·seed 전용으로 일반화하지 않는다. 이동·병합·squash·삭제·운영 재적용은 별도 승인 범위다.
- local SQL, remote 적용, 사용자 권한 서버 결과, 앱 E2E를 구분한다. remote가 필요한 주장은 승인된 최소 metadata/실행 근거로 확인하고 없으면 UNKNOWN으로 둔다. 문서 작업을 이유로 운영 접속하지 않는다.

<a id="delivery"></a>
## 보존·전달·보고

- 수정 직전 현재 bytes와 HEAD blob, 기존 index·dirty를 고정한다. 문서 개편처럼 원문 보존이 필요한 작업은 승인된 저장소 밖 위치에 복사하고 독립 복원 hash·별도 inode를 확인한다. 비밀·무관한 자료를 불필요하게 복제하지 않는다.
- 삭제·정리에는 별도 정확한 대상 승인이 필요하다. 디스크 [15 GB 기준](../project-memory/핵심-결정사항.md#2026-11-11-작업-장비-저장공간-기준)은 재생성 가능 산출물 확인과 보호 범위 판정을 요구하며 사용자 파일·공유 캐시·증적의 자동 삭제 권한이 아니다.
- 변경한 역사 본문의 출처·전체 문맥·표식·링크를 대응한다. 짧은 반복 문자열의 전역 첫 일치로 보존 위치를 결정하지 않는다. 원본 버전·제목·인접 블록·최종 hash를 연결한다.
- [변화 기반 갱신](advanced-codex-memory.md#update-triggers)으로 필요한 문서만 갱신한다. 읽기 전용이면 갱신 필요성을 보고만 한다.
- 실제 candidate와 staged diff를 대조하고 승인된 경로·구간만 commit한다. 다른 dirty를 편승시키거나 전체 stage·강제 push·이력 재작성하지 않는다. 일반 push 뒤 고정 commit의 원격 본문과 동일 SHA 필수 CI를 확인한다.
- 전체 파일 일치와 선택 구간 일치를 구분한다. 원격/CI 확인 실패는 전달 미완료이지 제품 실패를 뜻하지 않는다. 무관한 제품·CI 설정을 고쳐 통과시키지 않는다.
- 착수: 유형·승인 범위·읽은 근거·수정 영역·위험. 마감: 왜 바꿨는가·실제 검증·재사용/한계·문서 반영·전달 여부·해결/진행/잔여/계획·정확한 다음 지점. 결과 양식이 수행하지 않은 검사나 문서 쓰기를 강제하지 않는다.

## 2026-10-05 PO 최신 정책: 디자인 반복 빌드 산출물 유지

- 디자인 수정들을 먼저 묶고 incremental Release build 1회 → `adb install -r` → PO Galaxy S24 직접 확인 순서로 진행한다. 후속 수정도 같은 순서를 반복한다.
- PO가 산출물 제거를 명시하기 전까지 project-local build output·`.cxx`·`.gradle`·task build-temp·캐시를 유지한다. `clean`이나 자동 post-task cleanup으로 다음 incremental build 기반을 지우지 않는다.
- 이 최신 지시는 아래 2026-10-04 자동 정리 정책과 기존 task의 cleanup 승인을 대체한다. 최종 디자인 승인만으로 산출물 삭제를 자동 실행하지 않는다. 삭제에는 새로운 명시적 PO 지시가 필요하다.
- APK·증적·소스·자산·QA·서명·개발 도구·개인 데이터 보존 계약은 유지한다. incremental은 기존 산출물 재사용 방식이며 변경 영향에 따라 일부 재빌드가 발생할 수 있다.
- 빌드·설치는 요청된 디자인 검토 범위에 한정한다. commit·push·Store·다음 작업 자동 시작은 별도 승인 계약을 따른다.

## 2026-10-04 PO 고정 정책: substantial task 종료

- 필수 APK/AAB·증적 복사 → hash·Git 보존 확인 → exact-path 재생성 산출물 안전 정리 → 디스크 전후 확인 → 보고 → STOP 순서를 지킨다.
- source·asset·migration·dirty·서명·SDK/NDK/CMake·wrapper·modules-2·node_modules·Codex·개인/시스템 데이터는 삭제하지 않는다. 과거 증적은 참조 여부가 불명확하면 보존한다.
- 대형 전역 캐시는 자동 포괄 승인 대상이 아니다. 이번 2026-10-04 통합 배치의 build-cache-1 ≥10GiB 삭제 승인만 별도 적용한다.
- RC는 정확한 committed source에 귀속한다. unrelated dirty는 보존·제외하며 모든 계절 QA 버튼은 새 PO 지시 전까지 유지한다. 미적 최종 승인과 Store 승인 권한은 PO에게 있다.
