# advanced-codex-memory.md

정보 종류별 근거·현재와 역사 구분·갱신 트리거·정정·인계를 소유한다. 2026-11-11 개편 기준이다. 대화 기억이나 최신 날짜만으로 프로젝트 사실을 확정하지 않는다. [실행 권한](advanced-codex-workflow.md#execution-contract)과 [검사](advanced-codex-checklist.md#evidence-contract)는 각 소유 문서를 따른다.

<a id="authority-map"></a>
## 사실별 근거 지도

| 질문 | 우선 확인할 근거 | 대체할 수 없는 것 |
| --- | --- | --- |
| 무엇을 실행할 수 있는가 | 시스템·보안·도구 권한 안의 현재 PO 승인 | 과거 명령·첨부 기획·문서의 실행 예시 |
| 어떤 동작·예외를 요구하는가 | 해당 범위의 승인된 정책·제품 계약과 [핵심 결정](../project-memory/핵심-결정사항.md#decision-scope-map) | 현재 코드만으로 요구 폐기 |
| 무엇이 구현됐는가 | 특정 source/트리/working tree·빌드 입력 | 설계 문서만으로 구현 완료 |
| 무엇이 적용됐는가 | 서버 반영·runtime·빌드·설치 영수증 | repo 파일 존재나 소스 SHA |
| 무엇이 수락됐는가 | [단일 수락 원장](../qa/nuri-integrated-closeout-2026-10-25.md)의 조건·후보·실행 증거 | CI·서버 계약만으로 기기/운영 PASS |
| 현재 요약·다음 행동 | [현재 상태](../project-memory/현재-프로젝트-상태.md#current-baseline), [우선순위](../project-memory/다음-작업-우선순위.md#resume-point) | 과거 로그의 '다음' |
| 왜 그때 그렇게 했는가 | [로그](../project-memory/최근-작업-로그.md), 아카이브·이전 승인·[리서치](../리서치/리서치.md) | 과거 PASS를 새 후보로 자동 전용 |

코드와 요구가 다르면 **요구 / 승인 / 구현 / 배포 / 수락 / 충돌 / 영향 / 권장 해결 / 필요한 결정**을 분리한다. 문서에 없다고 운영에도 없다고 추정하지 않는다. 필요한 remote 확인이 승인되지 않았거나 근거가 없으면 UNKNOWN으로 남기고 독립적인 승인 작업은 계속한다.

[NURI-CANONICAL-SOURCE-OF-TRUTH](../project-memory/NURI-CANONICAL-SOURCE-OF-TRUTH.md)는 2026-08-05 기준선과 당시 우선순위의 역사 자료다. 그 문서의 '코드 우선'은 요구·승인·실제 수락을 취소하지 않는다. [release-checklist](../qa/release-checklist.md)의 날짜별 후보·Room 배정·설치 대기도 당시 범위다. 현재 실행 대기열로 다시 활성화하지 않으며 개별 보호 조건은 후속 근거 없이 폐기하지 않는다. 두 파일은 이번 개편에서 수정하지 않는다.

<a id="reading"></a>
## 필요한 만큼 읽고 다시 확인하기

1. 적용 AGENTS와 [Workflow 실행 핵심](advanced-codex-workflow.md#execution-contract), 현재 상태·우선순위·직전 관련 로그를 확인한다.
2. 변경 종류에 맞는 Checklist와 관련 결정·승인 기획·원장 행·소스·증거를 읽는다. SQL은 [실제 소비 가이드](../sql/정리-가이드.md), 기술 판단은 리서치의 해당 절로 확장한다.
3. 새 세션·컨텍스트 유실·읽은 파일 hash 변경·승인 범위 변경 시 관련 핵심을 다시 읽는다. 같은 파일의 변경 없는 긴 이력을 매 세부 작업마다 반복하지 않는다.
4. 읽은 경로·버전/hash·절과 미확인 범위를 남긴다. 링크가 있다는 것과 원문을 읽었다는 것은 다르다. 코드 읽기를 모든 문서 완독 뒤로 강제하지 않는다.

<a id="instruction-loading"></a>
## 지침 발견과 적용 확인

공식 발견 순서는 [OpenAI AGENTS 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 참고하되 실제 클라이언트·작업 경로·설정과 구분한다. 자동 주입 합계 제한과 도구로 읽은 MD 전체 크기는 다른 지표다. 로드 한도·모델·전역 설정을 임의 변경하지 않는다.

2026-11-11 이 개편 세션에서는 Room B 경로의 AGENTS 지침이 대화에 제공됐고, 실제 수정 대상은 PO가 지정한 Master worktree다. Master AGENTS와 engineering 문서는 도구로 읽었다. Master 경로의 새 지침이 자동 주입됐다는 증거는 아니다. 전역 AGENTS는 읽기 근거로 확인했으나 전역·다른 checkout·스킬·플러그인은 수정하지 않았다.

새 정상 실행에서는 실제 시작 경로와 적용 AGENTS/override, 확인된 fallback 설정, 본문 hash를 대조한다. 다음 다섯 분류로 기록한다: **자동 주입 확인 / 자동 후보·미확인 / 명시적 읽기 연결 / 태스크 조건부 / 역사 자료**. 파일 존재만으로 자동 로드라고 쓰지 않는다. 숨은 추론·세션 비밀 로그·인증 파일을 수집하지 않는다.

정적 문서 평가, 모의 판단, NEXT_RUN_INSTRUCTION_LOAD, REAL_TASK_OBSERVATION은 독립 상태다. 새 실행과 실제 제품 작업을 하지 않았으면 뒤 두 상태는 PENDING이다. 저장·현재 도구 읽기만으로 모든 세션에 적용됐다고 하지 않는다.

<a id="update-triggers"></a>
## 변화 기반 갱신

| 바뀐 사실 | 갱신할 소유 문서 | 남길 최소 내용 |
| --- | --- | --- |
| 최신 구현·배포·설치·미완료 요약 | 현재 프로젝트 상태 | 종류별 기준과 마지막 확인 시점·한계 |
| 실행 순서·선행 조건·승인·보류 | 다음 작업 우선순위 | 단일 현행 큐·정확한 재개점 |
| 의미 있는 수행·실패·수정 | 최근 작업 로그 | 왜·달라진 것·검증/한계·당시 다음 |
| 정책·조건·예외 | 핵심 결정사항 | 승인 출처·대상·후속 관계·유효 범위 |
| 새 기술 판단 | 리서치 | 배경 → 문제 → 선택지 → 결정 이유 → 리스크 → 다음 액션 |
| 실제 수락 변화 | 단일 원장 및 연결 증거 | 조건 ID·후보·환경·결과·재사용·한계 |
| 도메인/운영 계약 변화 | 해당 소유 문서 | 승인된 변경과 소비 영향 |

변화 없는 문서는 쓰지 않는다. 읽기 전용 요청에서는 필요한 갱신을 제안할 뿐 저장소 쓰기를 만들지 않는다. 장문 결과를 여러 메모리에 복제하지 않는다. 원장 수정 권한이 없으면 새 수락을 기록하지 않고 기존 판정의 위치만 연결한다.

<a id="current-history"></a>
## 현재값과 역사·정책

- 현재 상태에는 문서 기준, 제품 source, runtime 입력, APK/설치, 서버·환경, 마지막 검증 시점을 분리한다. 현재 실측하지 않았다면 '마지막 확인'으로 적는다. QA 환경·운영 환경·미배포 변경은 별도다.
- 우선순위는 한 개의 현행 대기열과 한 개의 정확한 재개점만 둔다. 완료 항목은 원장·로그·고정 Git으로 연결한다. 보류·외부 대기·미승인 제안은 현재 실행 행과 분리한다.
- 결정은 지속 정책, 사건 한정, 명시적 후속 대체, 현재 적용성 미확정으로 분류한다. 날짜가 최신이라는 이유로 다른 범위의 결정을 폐기하지 않는다. 과거 '현재'·'다음'·STOP·PASS를 오늘의 권한·상태로 읽지 않는다.
- 과거 고유 원문·실패·후보·검증 한계는 보존한다. 원격 고정 commit/blob, 기존 아카이브, 수정 직전 보존본으로 출처·내용 hash를 연결한다. 미전달 고유 원문은 로컬에 남기거나 별도 보존·대응을 확보하고 공개 범위를 명시한다.
- 로그 20개 초과 같은 숫자는 검토 신호이지 자동 이동·삭제 권한이 아니다. 아카이브는 참조·전체 블록·복구·승인을 확인한 별도 범위이며 새 거대 복제 문서를 반복 만들지 않는다.
- 가이드 CMS 정책은 해당 도메인의 승인 범위만 가진다. SQL은 실행 이력·재구축·계약 검사·참고·seed·복구 등 실제 소비로 구분하며 seed 전용으로 일반화하지 않는다.

<a id="correction"></a>
## 충돌 정정과 보존

1. 같은 주장의 판본·경로·hash·날짜·후보·환경부터 비교한다. ZIP·Desktop·다른 worktree의 동명 파일을 최신본으로 가정하지 않는다.
2. 충돌 정보의 종류를 근거 지도에 대입한다. 불명확한 원인은 가설로 기록하고 필요한 확인을 분리한다.
3. 승인된 소유 문서의 해당 구간만 고친다. 쓰기 직전 시작 hash가 달라졌으면 동시 변경을 먼저 보존·대조한다.
4. 이전 문장·제목 계층·BEGIN/END·최종 보존 위치를 연결한다. 짧은 반복 문자열 첫 일치, 코드 fence 안의 #를 실제 제목으로 취급하지 않는다.
5. 관련 안내만 선택 동기화하고 로그에 정정 이유·범위·원문 연결을 남긴다. read-only면 보고만 한다. 사용자 dirty 전체를 복원·삭제하지 않는다.

<a id="handoff"></a>
## 인계와 근거 접근 범위

한 작업의 인계에는 실제 승인/금지, source·문서·runtime·서버·설치 기준, 변경 ID 또는 고정 커밋, 증거 위치·해시, 결과/재사용·미실행·보류, 보호한 dirty·QA 자료, 정확한 다음 한 지점을 연결한다. 추적 ID는 기존 원장 ID를 우선하며 필요할 때만 DEC/LOG/CHG/RISK 날짜 ID를 추가한다.

저장소 밖 캡처·영수증·원본은 비공개 로컬 근거다. 링크 존재, 파일 존재 확인, 내용 읽기, 재실행 검증을 각각 구분한다. 비밀값·개인 캡처·인증 원문을 문서나 Git에 복제하지 않는다. UNKNOWN·명시적 검토용 placeholder·합성 QA는 허용하되 실제 운영 정보나 수락값으로 게시하지 않는다.

[전달 규칙](advanced-codex-workflow.md#delivery)에 따라 전체/선택 구간을 대조하고 commit·push·동일 SHA CI·원격 접근 여부를 남긴다. 최종 SHA만 넣으려 내용 없는 반복 커밋을 만들지 않는다. 해결/진행/잔여/잔여 해결 계획과 현재 승인 종료·후속 조건을 구분한다.
