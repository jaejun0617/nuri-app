# Walk final-deletion receipt — server corrective

2026-10-21 · NURI-09 · server contract only. Native integration, crash/disk/device proof and the final Privacy Gate remain with the serial Walk Owner. Existing route/session/Memory deletion contracts are separate and unchanged.

## Scope and dependency

Forward migration `20261020190315_walk_final_deletion_receipt.sql` adds one table in the existing unexposed `walk_private` schema. It changes no global Account/Pet function, RLS, grace period, Auth flow or previously applied Walk migration.

This is **Walk-owned schema plus global referenced-delete failure/lock dependency**, not zero global impact. FK `ON DELETE SET NULL` actions update the new table and run its protected BEFORE UPDATE finalizer in the same transaction. Proof failure rolls back the entity deletion. There are no new custom triggers on Auth/Pet/global request tables; PostgreSQL adds its normal RI constraint triggers.

ACCOUNT uses non-null `owner_ref` to Auth and null `pet_ref`. PET uses non-null `pet_ref` and null `owner_ref`; its authenticated non-null owner identity is validated and hashed separately. This avoids a new Auth-lock-then-Pet-lock inversion in the existing pets-before-Auth account finalizer. Only the scope-relevant non-null→null FK transition confirms FINAL. Initial null, grace status, compat completed, empty lookup, zero affected or a failed request never confirms it.

## RPCs and response

All return jsonb, SECURITY DEFINER, `search_path=public, pg_catalog`, PUBLIC/service_role EXECUTE denied.

| RPC | Parameters | EXECUTE |
| --- | --- | --- |
| prepare_walk_final_deletion_v1 | p_request_id uuid, p_purpose text, p_pet_id uuid, p_capability text | authenticated only |
| recover_walk_final_deletion_v1 | p_request_id uuid, p_purpose text, p_capability text | explicit anon/authenticated |
| ack_walk_final_deletion_v1 | same as recover | explicit anon/authenticated |

Purpose is exactly ACCOUNT_FINAL or PET_FINAL. Account pet is null; Pet pet is the actual owned UUID. No owner UUID input exists. Capability is 32 cryptographically random bytes generated by Native and encoded as64 lowercase hex characters. Persist it encrypted before networking; never generate a new one for a retry. The server validates encoding, not entropy, and stores only purpose/request/resource-bound HMAC, never the raw capability.

Response fields are exactly version1, requestId, purpose, resourceBinding, state, registeredAt, confirmedAt, acknowledgedAt. State is PENDING, FINAL or ACKNOWLEDGED. Timestamps use the existing Walk UTC wire convention. No owner/Pet UUID, raw route, coordinates, measurements, body or media is returned/copied.

Prepare revalidates live Auth and real Pet ownership, locks only the relevant target row, then takes an owner-registration lock. Exact pending identity replays; purpose/resource/capability conflict rejects. Independent devices can register separate watches for the same resource; all finalize together. Maximum64 unacknowledged watches per verified owner bounds fanout without an abandoned-device monopoly. Receipt operations never lock back from a receipt to its target.

## Identity, generation and retention

Auth created_at is nullable in the actual schema; missing generation is denied, not guessed or repaired. Pet created_at has the existing NOT NULL constraint. A timestamp is not independently authoritative or globally immutable: final authority is the original FK lifecycle. Completion nulls that reference permanently. Same-UUID recreation, including a copied timestamp, cannot reattach or revive a FINAL/ACKNOWLEDGED request. A changed pending generation conflicts rather than rebinding. No global timestamp/identity constraint is added.

Unacknowledged minimal proof has no unattended expiry, so long-offline recovery does not depend on JWT lifetime. ACK is accepted only after FINAL; repeated ACK returns the same bound proof/timestamps. It clears redundant owner_binding/pet_binding hashes. The remaining hashed request/purpose/resource/capability tombstone and receipt timestamps are retained to prevent request-ID reuse and support exact replay. This is **not physical row removal**. Target raw references are already null at FINAL. No purge/TTL/global retention policy is introduced.

An already-absent resource without prior registered proof remains unavailable/UNKNOWN. Existing legacy unconfirmed tickets cannot gain retroactive proof. Missing or unusable local capability/Keystore cannot be repaired by looking at an empty resource list. Never classify those cases as deleted.

## Exact Native handoff — not implemented here

1. Explicit deletion only: durably encrypt/readback request/capability/captured owner+resource scope before prepare. Do not start GPS or delete local data.
2. `walkFinalDeletionRepository.prepare(intent, signal)` requires a captured-context AbortSignal. Abort it on owner/foreground generation change. Production transport has an absolute15s deadline and aborts the request; late prepare cannot authorize deletion continuation. A timed-out prepare may have committed, so preserve/reconcile the same identity.
3. Persist the returned resource binding into that same journal, then call the existing Account/Pet deletion path. Do not replace the global delete contract with this prepare RPC; prepare never deletes anything.
4. On restart use the capability-only recover path, including after Auth deletion/JWT expiry. The production adapter sends only project client key + JSON body, omits Authorization/cookies/session storage and has15s deadline. Do not send an expired global JWT or call getUser/refresh as a recovery prerequisite.
5. FINAL for the exact captured request/purpose/resource binding can confirm the existing Native journal. Never apply an old proof to current Selected Pet, a recreated entity generation, a new capture or a foreign owner's data. Extend the Native capture/generation fence accordingly; this server adapter alone is not that lifecycle implementation.
6. Only after durable local confirmation and verified exact-scope cleanup call `ack(intent, finalProof, true)`. ACKNOWLEDGED is replay evidence, not a new permission to delete another local scope. ACK must not be called as a substitute for Native cleanup completion. The server cannot attest local disk completion.

Existing `finalDeletion.ts`/Native flows were not edited in NURI-09. Native process-death, key invalidation, pending journal recovery and device cleanup gates must be completed by the Walk Owner before Privacy PASS.
